ТЗ: Развитие Presentation Engine — расширение выразительных средств визуализации

#1. Цель

Расширить существующий Presentation Engine проекта Temporality новыми способами визуального представления информации, сохранив текущую архитектуру, декларативную модель Presentation IR и единый механизм рендеринга.

Основная задача — дать агентам возможность выражать более широкий спектр аналитических идей: позиционирование объектов, многомерное сравнение, распределение, иерархии, потоки, процессы и взаимосвязи.

Развитие должно происходить эволюционно, без создания отдельной подсистемы визуализации и дублирования существующих механизмов.

Ключевой принцип: агент описывает данные и смысл визуализации, Presentation Engine отвечает за её представление.

#2. Архитектурные ограничения

Использовать существующие компоненты:

  • kernel/presentation/ir.go — Presentation IR.
  • kernel/presentation/registry.go — Component Registry.
  • kernel/presentation/components.go — типизированные структуры и валидация.
  • kernel/presentation/layout_viz.go — визуализация и построение layout.
  • Существующие SVG, PNG и Text renderers.
  • kernel/presentation/adapt.go — адаптация под возможности каналов.
  • kernel/agent/presentationtools.go — инструменты агента и описание каталога IR.
  • docs/presentation-engine.md — архитектурная документация.

Необходимо сохранить:

  1. Renderer-agnostic Presentation IR.
  2. Единый источник данных для всех форматов отображения.
  3. Обязательную поддержку Native UI, SVG, PNG и Text.
  4. Строгую типизацию и валидацию входных данных.
  5. Централизованный Component Registry.
  6. Отсутствие исполнения произвольного кода из IR.
  7. Совместимость с существующими документами IR версии 1.0.

Не вводить обязательную зависимость от конкретной JS-библиотеки визуализации. Допускается использование существующих механизмов и внешних библиотек за renderer-адаптерами.

#3. Этап P0. Завершение базового каталога визуализаций

Перед добавлением новых возможностей необходимо привести существующую реализацию в соответствие с заявленной спецификацией.

#3.1. Scatter Chart

Добавить поддержку диаграмм рассеяния.

Требования:

  • Двумерные координаты X/Y.
  • Подписи осей.
  • Минимальные и максимальные значения осей.
  • Автоматическое определение диапазонов при отсутствии явных ограничений.
  • Подписи точек.
  • Индивидуальные размеры и стили маркеров.
  • Группировка точек.
  • Легенда групп.
  • Отображение значений при наличии места.
  • Обработка отрицательных и нулевых значений.
  • Корректное отображение нескольких точек с одинаковыми координатами.

Структура данных должна поддерживать независимые объекты с координатами, а не только массивы последовательных значений.

#3.2. Heatmap

Добавить тепловые карты.

Требования:

  • Двумерная матрица значений.
  • Подписи строк и столбцов.
  • Цветовая шкала.
  • Отображение числовых значений в ячейках.
  • Обработка отсутствующих значений.
  • Настраиваемые границы шкалы.
  • Поддержка отрицательных значений.
  • Подписи шкалы и единицы измерения.

#3.3. Histogram

Добавить гистограммы распределения.

Требования:

  • Автоматическое или заданное количество интервалов.
  • Возможность указать ширину интервала.
  • Отображение частот.
  • Подписи осей.
  • Поддержка нормализованного распределения.
  • Корректная обработка пустых и малых выборок.

#3.4. Timeline Chart

Проверить необходимость отдельного типа временного графика.

Если существующий chart может выразить временной ряд без потери семантики, использовать его. В противном случае реализовать специализированный тип с временной шкалой.

#3.5. Согласованность каталога

Провести сверку:

  • Документации.
  • Реестра компонентов.
  • Типизированных структур.
  • Валидаторов.
  • Agent Tool Catalog.
  • Native UI renderer.
  • SVG renderer.
  • PNG renderer.
  • Text fallback.

Ни один компонент не должен рекламироваться агенту как поддерживаемый, если он не реализован полностью.

#4. Этап P1. Новые выразительные средства

#4.1. Positioning Map / Quadrant

Приоритет: высокий.

Предназначение: позиционирование объектов в двумерном пространстве по двум независимым характеристикам.

Примеры применения:

  • Конкурентный анализ.
  • Стратегическое позиционирование.
  • Сравнение продуктов.
  • Оценка рисков.
  • Матрица приоритетов.
  • Оценка возможностей и зрелости.

Функциональность:

Оси:

  • Название и описание.
  • Минимум и максимум.
  • Подписи крайних значений.
  • Направление и формат отображения.
  • Возможность отображения нулевой линии.

Объекты:

  • X/Y координаты.
  • Название.
  • Группа.
  • Размер маркера.
  • Цвет или статус.
  • Дополнительное описание.
  • Признак выделения.
  • Необязательная ссылка на артефакт Temporality.

Пространственные элементы:

  • Вертикальные и горизонтальные reference lines.
  • Разделение на квадранты.
  • Названия квадрантов.
  • Подложки и выделенные области.
  • Целевые зоны.
  • Подписи и аннотации.
  • Обозначение свободных областей.

Отображение:

  • Автоматическое размещение подписей без существенного перекрытия.
  • Возможность компактного представления.
  • Легенда групп.
  • Выделение целевых и выбранных объектов.
  • Сохранение пропорций координатного пространства.

Positioning Map может быть реализован как специализированный IR-компонент или как профиль расширенного Scatter Chart. Предпочтительно повторно использовать общий координатный renderer.

#4.2. Radar Chart

Предназначение: многомерное сравнение объектов по набору характеристик.

Функциональность:

  • Набор измерений.
  • Несколько сравниваемых объектов.
  • Значения по каждому измерению.
  • Индивидуальные серии.
  • Подписи осей.
  • Минимальные и максимальные значения.
  • Легенда.
  • Выделение выбранного объекта.
  • Отображение числовых значений.

Применение:

  • Сравнение продуктов.
  • Оценка компетенций.
  • Оценка зрелости подразделений.
  • Сравнение моделей и агентов.
  • Профилирование возможностей.

#4.3. Sankey Diagram

Предназначение: визуализация потоков между состояниями, категориями и участниками.

Функциональность:

  • Узлы.
  • Направленные связи.
  • Вес или объём потока.
  • Подписи связей.
  • Группировка узлов.
  • Цветовое выделение потоков.
  • Отображение итоговых объёмов.
  • Контроль пересечений и читаемости.

Применение:

  • Распределение ресурсов.
  • Движение задач.
  • Воронки преобразования.
  • Распределение нагрузки.
  • Переходы между состояниями.
  • Использование ресурсов агентами.

#4.4. Swimlane Diagram

Предназначение: представление процессов с разделением ответственности между участниками.

Функциональность:

  • Дорожки участников.
  • Этапы процесса.
  • Действия и события.
  • Переходы между дорожками.
  • Условия переходов.
  • Параллельные ветви.
  • Начальные и конечные состояния.
  • Выделение ответственных.
  • Статусы элементов.

Не следует сводить Swimlane к обычному Flowchart. Участник и его дорожка являются самостоятельными семантическими элементами.

Применение:

  • Бизнес-процессы.
  • Взаимодействие подразделений.
  • Работа мультиагентных систем.
  • Процессы согласования.
  • Human-in-the-loop сценарии.

#4.5. Treemap

Предназначение: визуализация иерархических данных через вложенные прямоугольные области.

Функциональность:

  • Иерархия объектов.
  • Размер области по числовому значению.
  • Цвет по дополнительному показателю.
  • Подписи.
  • Вложенность.
  • Легенда.
  • Выделение объектов.
  • Поддержка нескольких уровней.

Применение:

  • Структура портфеля.
  • Распределение ресурсов.
  • Организационные структуры.
  • Распределение задач.
  • Анализ использования ресурсов.

#5. Этап P2. Дополнительные возможности

Рассмотреть и реализовать при наличии подтверждённых сценариев использования:

  • Funnel — визуализация последовательного сужения потока.
  • Decision Tree — дерево решений.
  • Priority Matrix — матрица приоритетов.
  • Calendar — календарные представления.
  • Расширенная Hierarchy — иерархические структуры.
  • Portfolio Map — специализированное представление портфеля объектов.

Не создавать самостоятельный компонент, если соответствующее представление может быть выражено существующим типом без потери семантики.

#6. Развитие Presentation IR

#6.1. Общие требования

Сохранить существующую структуру:

  • type
  • id
  • content
  • data
  • props
  • items
  • children
  • actions

Новые типы должны использовать те же правила разделения содержимого и параметров представления.

#6.2. Расширение модели Chart

Расширить ChartData и ChartProps для поддержки:

  • Координатных точек.
  • Нескольких серий.
  • Категориальных и числовых осей.
  • Настраиваемых диапазонов.
  • Подписей осей.
  • Легенд.
  • Reference lines.
  • Аннотаций.
  • Группировок.
  • Дополнительных измерений.

Не ломать существующий контракт labels / values / series.

#6.3. Новые типы компонентов

Каждый новый компонент должен иметь:

  • Типизированную структуру данных.
  • Типизированные props.
  • Строгий валидатор.
  • Регистрацию в Component Registry.
  • Native UI renderer.
  • SVG renderer.
  • PNG renderer.
  • Text fallback.
  • Описание в Agent Tool Catalog.
  • Документацию.
  • Тестовые примеры.

#6.4. Ссылки на сущности Temporality

Предусмотреть возможность связывать элементы визуализаций с существующими сущностями:

  • Артефактами.
  • Задачами.
  • Проектами.
  • Запусками агентов.
  • Другими доступными объектами.

Не дублировать модели предметной области внутри Presentation IR.

Ссылка должна содержать идентификатор и тип целевой сущности. Проверка прав доступа и разрешение ссылки выполняются на стороне runtime.

#7. Композиция визуализаций

Развить возможности комбинирования компонентов в одном Presentation Document.

Поддержать сценарии:

  • Заголовок и пояснение.
  • KPI и график.
  • Матрица и таблица подробностей.
  • Несколько связанных графиков.
  • График и текстовые выводы.
  • Диаграмма и список рекомендаций.

Использовать существующие card и card-grid как основу композиции.

Не вводить отдельную модель Dashboard, если существующая композиция Presentation IR покрывает задачу.

В дальнейшем предусмотреть синхронизацию фильтров и выделения между связанными компонентами.

#8. Интерактивность

Интерактивность должна развиваться в рамках существующей декларативной модели Actions.

Предусмотреть:

  • Выбор точки или объекта.
  • Раскрытие подробностей.
  • Переход к связанному артефакту.
  • Включение и отключение групп.
  • Фильтрацию данных.
  • Переключение представлений.
  • Выбор временного диапазона.

Произвольный JavaScript из Presentation IR не исполняется.

Интерактивные действия должны проходить через существующий механизм проверки разрешений и обработки Actions.

SVG и PNG должны сохранять смысл визуализации без интерактивных возможностей.

#9. Требования к рендерерам

#Native UI

Обеспечить:

  • Адаптивное отображение.
  • Корректную работу на узких экранах.
  • Интерактивность.
  • Подсказки.
  • Легенды и фильтры.
  • Раскрытие подробностей.
  • Сохранение читаемости при большом количестве элементов.

#SVG

Обеспечить:

  • Полноценную статическую визуализацию.
  • Корректные подписи.
  • Легенды.
  • Цветовое кодирование.
  • Сохранение пропорций.
  • Отсутствие зависимости от JS.

#PNG

Формируется из того же Drawing Model, что и SVG.

Обеспечить идентичность содержания и геометрии SVG- и PNG-представлений.

#Text

Текстовый fallback должен передавать смысл визуализации, а не просто сообщать её название.

Например, для Positioning Map необходимо выводить:

  • Названия осей.
  • Группы объектов.
  • Положение объектов.
  • Выделенные объекты.
  • Основные наблюдения.

Для Sankey — основные узлы и потоки с их значениями.

Для Heatmap — табличное представление матрицы.

#10. Инструменты агента

Обновить presentationIRCatalog в kernel/agent/presentationtools.go.

Агент должен получать:

  • Список доступных типов.
  • Описание назначения.
  • Поля и ограничения.
  • Примеры корректного IR.
  • Поддерживаемые режимы отображения.

Описание должно оставаться достаточно компактным, чтобы не расходовать контекст модели на избыточную документацию.

Необходима синхронизация каталога с реестром и валидаторами.

Рекомендуется добавить автоматическую проверку соответствия типов и их описаний.

В перспективе можно предусмотреть отдельный инструмент получения подробной спецификации компонента по запросу агента, но это не обязательное условие первой реализации.

#11. Производительность и ограничения

Сохранить существующие ограничения Presentation IR.

Дополнительно предусмотреть:

  • Ограничение количества точек и узлов.
  • Ограничение глубины иерархий.
  • Защиту от чрезмерной детализации.
  • Контроль сложности геометрического layout.
  • Ограничение размера итогового SVG.
  • Ограничение времени рендеринга.
  • Детерминированность результата при одинаковых данных и параметрах.

Для больших наборов данных предусмотреть упрощение отображения или явное сообщение об ограничении.

Нельзя молча удалять или искажать исходные данные.

#12. Тестирование

Для каждого нового компонента обязательны:

  1. Тесты разбора IR.
  2. Тесты строгой валидации.
  3. Тесты корректных и некорректных данных.
  4. Тесты граничных значений.
  5. Тесты Native UI renderer.
  6. Тесты SVG renderer.
  7. Тесты PNG renderer.
  8. Тесты Text fallback.
  9. Тесты адаптации к каналам.
  10. Проверка идентичности данных между форматами.

Подготовить набор эталонных визуализаций для автоматического regression testing.

Отдельно проверить:

  • Пустые данные.
  • Очень большие значения.
  • Отрицательные значения.
  • Отсутствующие значения.
  • Пересекающиеся подписи.
  • Большое количество категорий.
  • Узкую ширину отображения.
  • Длинные названия объектов.

#15. Критерии приёмки

Работа считается выполненной, если:

  1. Все новые компоненты зарегистрированы в Component Registry.
  2. Все компоненты проходят строгую валидацию.
  3. Каждый компонент поддерживает все обязательные форматы отображения.
  4. Native UI, SVG и PNG используют согласованную модель данных.
  5. Text fallback сохраняет семантику визуализации.
  6. Agent Tool Catalog содержит актуальные схемы.
  7. Старые Presentation IR документы продолжают корректно обрабатываться.
  8. Документация соответствует фактической реализации.
  9. Все новые возможности покрыты автоматическими тестами.
  10. Агент способен самостоятельно сформировать новые типы визуализаций на основании описания их контрактов.

#16. Ожидаемый результат

Presentation Engine должен стать более выразительным инструментом коммуникации агентов с человеком.

Агент должен уметь выбирать подходящую форму представления в зависимости от характера информации:

  • Сравнение объектов — сравнительные таблицы и Radar.
  • Позиционирование — Positioning Map.
  • Распределение — Histogram и Heatmap.
  • Потоки — Sankey.
  • Процессы — Swimlane.
  • Иерархии — Treemap и Mindmap.
  • Динамика — Timeline и Chart.
  • Зависимости — Dependency Graph.

Развитие не должно превращать Presentation Engine в BI-систему или отдельный конструктор дашбордов.

Это универсальный декларативный язык визуальной коммуникации агента, интегрированный с остальной архитектурой Temporality.
