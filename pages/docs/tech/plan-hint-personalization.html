Персональные подсказки: фактор B6 «работало именно у этого пользователя»

Статус: техпроект, не начат Компонент: Observation — observation.FindHints + activateObservationHints Зависит от: docs/plan-priming-relevance.md (§3.3 факторы, §8 детерминизм, §11 цикл полезности, §12 бенчмарк) и правок «вариант 1+2» (hint_query + подавление по истории задачи) — они уже в main Дата: 2026-11-14

#1. Проблема

Исходная жалоба: «при старте рана подсказки бестолковые каждый раз; возможно, стоит ранжировать знания по корреляции с конкретным пользователем и тем, чем он последние несколько ранов занимается».

Два первых дефекта закрыты:

  • query теперь — последнее сообщение пользователя (hint_query), а не сырой транскрипт, и длинный query усекается с обоих концов;
  • повторы между ранами одной чат-задачи подавляются по истории hint.offered задачи на task.priming.

Остаётся третий: ранжирование не знает, с кем говорит. Текущая сортировка отвечает на «что релевантно задаче» (matchTier) и «что доказано в целом» (stateTier / B4), но не на «что уже сработало у этого человека недавно и что ему уже вредило». Метрика полезности B4 (usefulnessTier) агрегирована по всем ранам проекта — для одного пользователя она обычно нейтрална (меньше 3 исходов), поэтому внутри массовых tier-3 совпадений решают kind/stale/tie-breaker по KnowledgeID, то есть фактически случайный порядок.

Важно развести два тезиса:

  • «пользователь редко меняет тему» — это уже покрыто лексическим и семантическим матчингом: тема совпадёт сама, отдельный фактор «о чём он думает» не нужен;
  • недостающая ось — персональная история успеха/неудачи и её свежесть: не тема, а то, что у этого человека уже сработало (или сломалось) и когда.

#3. Гипотеза и метрики успеха

H1. Знание, которое этому пользователю помогало недавно, должно обгонять равное по матчу знание, о котором о нём ничего не известно; знание, которое ему уже вредило, — не возвращаться в топ.

Наблюдаемые следствия:

  1. В чате, где три рана подряд решалась одна задача, персонально проверенные знания не уступают случайному совпадению по двум токенам.
  2. Доля повторных выдач hint.offered с уже виденными этому actor knowledge_id за окно падает (считается из телеметрии, без новой инфраструктуры).
  3. Бенчмарк §12: полы не проседают, персональные кейсы переворачивают порядок в нужную сторону.

Метрика «качество ≠ поведение» (§12.2) остаётся ручным пилотом: поведение агента с/без персонализации сравнивается отдельно, автоматически в CI не доказывается.

#4. Дизайн

#4.1 Сигнал B6 (этап 1 — только свежесть)

Три уровня, целые числа, как у остальных факторов:

Значение Условие
0 (boost) hint.used этого actor по знанию внутри окна
1 (нейтрально) данных по этому actor нет — новый человек, extraction выключен, сигнал не собрался
2 (demote) hint.outcome = harmful этого actor по знанию внутри окна

Окно: hintActorWindowDays = 14 — считается от occurred_at одним запросом (§4.3). Альтернатива «последние hintActorWindowRuns = 8 ранов actor» семантичеснее для редких, но разбросанных во времени пользователей, однако требует агрегации по ранам вместо фильтра по времени — на этап 1 не берём. Обе величины подбираются бенчмарком и фиксируются константами рядом с hintOutcomeMinSamples.

Почему не «игнорировал»: hint.ignored пишется на каждую невостребованную подсказку каждого рана — это шум, а не отрицательный опыт; demote только по явному harmful. Почему не used как полезность: used ≠ helpful (§11), поэтому used даёт лишь свежесть, а не доказательство пользы.

Этап 2 (опционально, после пилота): персональный B4 — доля helpful/harmful этого actor вместо глобальной, с тем же порогом по выборке. Отдельным этапом, потому что выборка на одного человека маленькая и шумная.

#4.2 Контракт данных

FindHints остаётся чистой функцией над журналом — история приходит явно:

// HintQuery
// ActorHistory — сигналы этого актора по знаниям, посчитанные вызывающим
// из журнала (hint.used / hint.outcome с context.actor.id). Nil = без
// персонализации, фактор нейтрален для всех кандидатов.
ActorHistory map[string]ActorSignal

type ActorSignal struct {
    LastUsedAt time.Time
    Harmful    bool
}

Так контракт тестируется без журнала, а корпус может подставлять историю напрямую.

#4.3 Источник и стоимость

A. On-demand выборка из журнала (рекомендуется, этап 1). ListObservationPage(Filter{Project, Actor, Types: ["hint.used","hint.outcome"], Order: "desc", Since: &window, Limit: 128}) → map[knowledgeID]ActorSignal. Тот же паттерн, что уже сделан в priorTaskIssued (observation/httpapi/server.go:1897).

B. Агрегация в проекцию Knowledge (пер-акторные счётчики рядом с HintOffers). Плюс — O(1) на запросе; минус — N акторов × M знаний в памяти проекции, новый контур агрегации и отдельное хранилище. Слишком дорого для этапа 1.

C. Кэш TTL поверх A (ключ project+actor, ~60 с), по образцу cachedKnowledge. Нужен, если A включается и в динамические активации.

Выбор: A + C, на первом этапе — только task.priming (один запрос на старт рана, как в варианте 2). Динамические активации подключаются после замера стоимости.

Обязательный пункт: индекс observation_events (project_id, actor_id, type, occurred_at DESC) — добавить в observation/postgres/migrations/observation_events_indexes.up.sql (файлы идемпотентны и гоняются на каждом буте, journalMigrations в observation/postgres/store.go:36) плюс соответствующий .down.sql. Без него выборка упирается в (project_id, occurred_at, …) и фильтрует actor/type на лету.

#4.4 Место в цепочке сортировки

Текущая цепочка (observation/hints.go:313-346):

matchTier → kindTier → stateTier → staleTier → usefulTier → noveltyTier → KnowledgeID

Рекомендация: вставить B6 между usefulTier и noveltyTier.

  • Ниже matchTier — релевантность задаче всегда главнее личной истории.
  • Ниже stateTier и staleTier — доверие и сомнение по §3.3: достоверность входит в допуск, а не слагается в рейтинг, поэтому challenged не всплывает над confirmed из-за того, что пользователю вчера помогло.
  • Ниже глобального B4 — «доказано полезным» сильнее «недавно потрогано».
  • Выше noveltyTier и tie-breaker по KnowledgeID — именно здесь решается массовая tier-3 равность, ради которой фактор и нужен.

Альтернатива (поднять сразу после stateTier, чтобы личное обыгрывало kind/stale) — не на старте: она даёт фактору больше власти, чем обосновано, и любой подъём меняет порядок в корпусе. Если пилот покажет, что фактор не чувствуется — поднять осознанно отдельным решением с пересчётом бенчмарка.

#4.5 Версионирование и детерминизм (§8)

  • HintsAlgorithmVersion → lexical-entity-topic.v4 (observation/hintrender.go:12) + обновить комментарий о полах в observation/priming_benchmark_test.go:42.
  • Детерминизм: вход детерминирован (история приходит явно, окно считается от query.Now, как уже делает staleTier). Now == 0 → окно выключено → фактор нейтрален; это же правило для корпуса без now.
  • Порядок кандидатов с одинаковыми признаками остаётся детерминированным: B6 — целое число, финальный tie-breaker — KnowledgeID.

#5. Этапы работ

  1. Контракт. HintQuery.ActorHistory + ActorSignal; actorHistoryTier(item, history, now) в observation/hints.go; вставка в цепочку сортировки (§4.4).
  2. Источник. actorHistory(...) в activateObservationHints (по образцу priorTaskIssued), только task.priming; TTL-кэш; телеметрия actor_history_count в hint.query.
  3. Индекс. Миграция (project_id, actor_id, type, occurred_at DESC) — до включения A в прод, иначе деградация на больших журналах.
  4. Версия. lexical-entity-topic.v4, обновление хардкодов/комментариев.
  5. Корпус. Расширить схему фикстур (§6) и добавить персональные кейсы; прогнать §12.3 — сравнение версий по всем метрикам.
  6. Наблюдаемость. Счётчики + способ посмотреть «почему этот кандидат поднялся» (§13).
  7. Пилот. Ручной behavioral impact (§12.2): один и тот же чат с фактором вкл/выкл.

#6. Тесты и бенчмарк

  • Юнит: actorHistoryTier — boost / neutral / demote / окно истекло / Now == 0; FindHints с историей и без — порядок меняется только там, где должен.

  • HTTP: activateObservationHints подставляет историю только для task.priming, при ошибке выборки деградирует в нейтральный фактор, не в 500.

  • Схема корпуса (observation/priming_benchmark_test.go:16-42) — дополнить:

    "query": { ..., "now": "2026-11-14T00:00:00Z",
           "actor_history": { "K-1": {"last_used_at": "...", "harmful": false} } }

    без now персональные кейсы не воспроизводимы — окно считается от текущего времени.

  • Новые кейсы: ≥5 — «личное поднимает равное», «harmful топит», «чужой актор не влияет», «история не переворачивает более сильный matchTier», «история не поднимает challenged над confirmed».

  • Инварианты CI остаются: stale leakage = 0, детерминизм, бюджет блока, полы precision ≥ 0.90, recall ≥ 0.85, redundancy ≤ 0.05, efficiency ≥ 5.0 (observation/priming_benchmark_test.go:45-50). По §12.3 изменение без улучшения на корпусе не принимается — для персонализации «улучшение» = пройденные персональные кейсы при неизменных полах.

#7. Наблюдаемость

  • hint.query: actor_history_count (сколько записей истории подано), actor_id уже есть в Context;
  • hint.offered: по желанию — признак «получил персональный буст», чтобы в трейсе было видно, почему кандидат поднялся (§13: reason);
  • панель Knowledge: пер-акторная статистика used/helpful — отдельной строкой позже (этап 2), не блокирует.

#8. Риски и открытые вопросы

# Риск Что делать
1 Окно по времени ломает воспроизводимость корпуса — ранер не передаёт Now Обязательный пункт схемы: now в фикстурах (§6)
2 used ≠ helpful — механическое отражение терминов даёт свежесть без пользы Этап 1 — только свежесть; персональный B4 отдельным этапом
3 Индекса по actor/type нет — выборка будет сканировать Миграция до включения (§4.3, этап 3)
4 Пузырь персонализации: буст закрепляет пользователя в знакомом, противоречит разнообразию §9 diversifyCandidates идёт после ранжирования и частично страхует; смотреть redundancy в бенчмарке
5 Пустая история (новый пользователь, extraction выключен, SkipKnowledge) Нейтральный уровень 1 — поведение не меняется, регрессии нет
6 Склейка human-requester — все неаутентифицированные раны делят один ключ (main.go:3588) Принять: это fallback, не продукт. Не класть в ключ ничего чувствительного
7 Косметическая нестыковка: context.actor.type всегда "agent", а id — человек (activities.go:3330) Ключом считать только id; править тип — отдельно, если понадобится UI
8 Стоимость на каждую активацию Этап 1 — только priming + TTL-кэш; замерить до расширения
9 Дрейф полос из-за изменения порядка в корпусе Отчёт §12.3 до/после, полы фиксируются комментарием в priming_benchmark_test.go

#9. Вне скоупа

  • Персонализация векторов/семантики (дообучение эмбеддингов на историю пользователя) — P2, только если бенчмарк упрётся в потолок лексики;
  • Отдельное персистентное «личное пространство знаний» пользователя и выделенный индекс;
  • Изменение lifecycle знаний, гейтинга и подавления (вариант 2 уже сделан);
  • Автоматический подбор весов факторов на каждом ране (§11: адаптация допустима, самообучение — нет);
  • Фактор «над какой темой пользователь работает последние N ранов» — это лексический/семантический матч, он уже есть.

#10. Критерии готовности

  • HintQuery.ActorHistory + B6 в цепочке сортировки на позиции §4.4;
  • HintsAlgorithmVersion = lexical-entity-topic.v4, тесты зелёные;
  • индекс (project_id, actor_id, type, occurred_at DESC) в миграции;
  • корпус: схема now/actor_history, ≥5 персональных кейсов, полы §12.2 не просели, отчёт сравнения версий приложен (§12.3);
  • actor_history_count в hint.query, пустая история деградирует в нейтральный фактор;
  • docs/plan-priming-relevance.md обновлён: B6 в §3.3, пункт в §8 (детерминизм окна), строка в статусе реализации.
