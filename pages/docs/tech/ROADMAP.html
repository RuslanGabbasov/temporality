#P1 — Sandbox security matrix

Automated security acceptance (not a sandbox platform).

Existing coverage in kernel/sandbox/docker_test.go:

  • ../ workspace escape — blocked (symlink escape test)
  • Docker socket / privileged — inaccessible (--cap-drop=ALL, no --privileged, image digest pinned)
  • Memory/CPU/PIDs — limited (args enforced in test)
  • Output — bounded (limited buffer truncation test)
  • Read-only workspace for reviewer/qa roles — enforced via args
  • Network egress — --network=none default / bridge only with granted access (args test + live check: none → curl exit 6, bridge → HTTP 200)
  • Credentials — only HOME/TMPDIR cross the boundary, nothing from the host env (args test)
  • Timeout — request context kills the run, container force-removed (test with fake docker)
  • /scratch — isolated between executions by construction (fresh container + private tmpfs per command)
  • Expected-vs-actual matrix doc with explicitly accepted risks (docs/sandbox-security-matrix.md)

#P1 — Channel driver layer

Source spec: docs/channels.md.

  • Phase 0 — extract the layer — ChannelDriver contract (spec/capabilities, settings schema, SendText/SendFile, pull Poller); matrix/telegram/slack/generic-webhook became drivers (kernel/agent/driver_*.go, one registration line); settings → JSONB payload (000051) + KERNEL_CHANNEL__* env aliases with legacy names kept, generic admin form from the driver schema; matrixInboundLoop → generic channelInboundLoop over every driver with a Poller, channel-neutral MatchChannelReplies, cursors + settings fingerprint persisted (000052). Dedup table and sender-identity verification land with the intake pipeline (phase 1, docs/inbound-messages.md). Push Webhook drivers and interactive options remain future work.
  • Telegram inbound driver — two-way telegram (kernel/agent/driver_telegram_inbound.go): getUpdates poller with a persisted offset cursor, private-chat identity (chat.id = from.id), document/photo attachments via getFile; zero edits outside the driver file beyond capabilities/settings declaration
  • New inbound channels as drivers — push model landed in the driver contract: Webhook() (Route/VerifyRequest/Parse/Respond) next to Poller(), and one shared receiver (channelWebhookReceiver) feeds verified pushes into the same pipeline as polls (dedup → reply matching → intake, serialized per channel). Mattermost driver: REST v4 posts + self-hosted outgoing webhooks (form-encoded, shared-token verification, trigger-word strip, base_url setting); Slack bot driver: Events API with v0 HMAC signatures + 5-min freshness window, url_verification handshake, threads carried as ReplyTo, bot/subtype events skipped, error envelopes (ok:false) surfaced from every Web API call. In-memory retry fence for webhook replays (at-least-once preserved). Interactivity stays a separate roadmap item
  • Mattermost inbound moved to WebSocket — mattermostPoller (kernel/agent/driver_mattermost_inbound.go): one WS connection per 25s poll window, authentication challenge with the same base_url+token pair, posted events parsed (post is a JSON-encoded string inside the payload), DMs included — which outgoing webhooks cannot serve; cursor = last seen create_at (ms), own posts excluded via users/me self. Outgoing-webhook adapter and the /v1/channels/mattermost/hooks route removed: deployments should delete the server-side webhook, the poller starts working with the credentials already configured
  • Interactivity — options as buttons where the channel supports them (Telegram inline keyboards, Slack blocks), text fallback everywhere

#Strategic conclusion

Temporality is at a transition point:

Phase 2: "We proved the model is correct"
    ↓
Next: "We made a system that people can use"
    ↓
Goal: "People use it to understand and improve agent experience"

The immediate goal is NOT to close all Phase 2 remnants.

The immediate goal:

Collect a minimum end-to-end working loop where a real person runs a real agent and Temporality turns the resulting experience into an investigable temporal picture.

Living Skills extend this loop: the skill a person installs becomes an observable, versioned capability whose usage produces memory and evidence.

After that, every experiment must be simultaneously:

  • acceptance corpus
  • real working scenario
  • source of product requirements

This way Temporality won't drift into "yet another debugger" or "yet another agent runtime".
