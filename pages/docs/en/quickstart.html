Getting started

Quick start

From zero to your first agent task — installation, onboarding, the first run.

#Requirements

  • Docker (Linux, macOS; Windows via WSL2). BuildKit recommended.
  • ~4 GB of free memory for the stack (PostgreSQL, Temporal, Journal, Kernel, UI).
  • A key from any OpenAI-compatible provider (OpenAI, OpenRouter, local Ollama, etc.).

#Run it

Prebuilt images from GHCR — the recommended path, nothing to clone or build:

mkdir temporality && cd temporality
curl -o docker-compose.yml https://raw.githubusercontent.com/RuslanGabbasov/temporality/main/docker-compose.yml
curl -o .env.example https://raw.githubusercontent.com/RuslanGabbasov/temporality/main/.env.example
cp .env.example .env
# edit .env: TEMPORALITY_MODEL_BASE_URL / _ID / _API_KEY
docker compose up -d

The latest published release comes up by default (images from the releases page ↗). For controlled upgrades pin a version: TEMPORALITY_VERSION=2026.2.113 docker compose up -d. Upgrading to a newer release: docker compose pull && docker compose up -d (or set the new pinned version) — the kernel migrates on start.

Building from source (for developing Temporality itself):

git clone https://github.com/RuslanGabbasov/temporality.git && cd temporality
cp .env.example .env
docker compose -f docker-compose.yml -f docker-compose.dev.yml up --build -d

This starts PostgreSQL, the Journal (:8080), the UI (:3000), Temporal (UI :8233), the Agent Kernel (:8090), SearXNG (127.0.0.1:8889, meta-search for the agent) and a headless browser. TEMPORALITY_MODEL_BASE_URL + _ID are the mandatory minimum; the kernel refuses to start without them.

Provider configuration examples:

# OpenAI
TEMPORALITY_MODEL_BASE_URL=https://api.openai.com/v1
TEMPORALITY_MODEL_ID=gpt-4.1-mini
TEMPORALITY_MODEL_API_KEY=sk-...

# Local Ollama
TEMPORALITY_MODEL_BASE_URL=http://host.docker.internal:11434/v1
TEMPORALITY_MODEL_ID=llama3.2
TEMPORALITY_API_KEY=

Stop the stack keeping the data: make stack-stop.

#Onboarding

Open http://localhost:3000. On the first visit an onboarding wizard walks you through the required steps and hides navigation until they are done:

  1. First project — a workspace for the agent's tasks.
  2. Administrator — your user.
  3. Model provider — base URL, key (stored in encrypted secrets), automatic model listing.
  4. Agent — from a template or from a plain-language description.
  5. Sandbox build — the image the agent's commands will run in (requires Docker daemon access).

Two cases where the wizard behaves differently:

  • KERNEL_AUTH_TOKENS is set — authentication was enabled by your own env: the wizard does not start anonymously. Sign in with one of those tokens (API-token mode) or comment the variable out for the anonymous flow;
  • KERNEL_SANDBOX_IMAGE is set — the sandbox image is pinned by your env: the build step offers Skip (rebuild via sandbox/build.sh).

#Your first task

Open Workspace — the agent chat — and write a task. The agent responds with streaming output; along the way it may:

  • run commands in the sandbox (/workspace of the project is persistent storage),
  • delegate subtasks to other agents (plan/delegate),
  • ask you a question through an approval card (in the chat, mirrored in "Runs"),
  • record a useful observation into the project's knowledge.

When it finishes, look at Runs (the step-by-step trace) and Knowledge (what the agent learned from the task).

#What to set up next

  • Channels — let the agent receive tasks from Matrix/Telegram/Slack and ask questions where you live: Inbound and channels.
  • Triggers — tasks on a schedule or on events: Triggers.
  • Skills — capture a repeating procedure: Skills.
  • Users and access — your team and RBAC: Administration.
