# Делегирование задач между агентами

## 1. Цель

Агент в ходе выполнения задачи должен уметь передать самодостаточную подзадачу
другому агенту и получить её результат — так же, как специалист передаёт задачу
коллеге с узкой компетенцией.

Делегирование — это runtime-инструмент `delegate`, доступный модели, а не
заранее сконфигурированный пайплайн. Состав команды не зашит в код: агент сам
решает, когда и к кому обратиться, в пределах выданных ему прав.

Пользователь при этом не составляет цепочки агентов вручную. Он лишь включает
агенту возможность делегирования и наблюдает результат в журнале.

---

## 2. Принципы

### Делегированный запуск — это настоящий run

Дочерняя задача выполняется как полноценный durable `AgentRun`
(Temporal child workflow): его можно отменить, он переживает рестарт воркера,
его траектория попадает в журнал Temporality.

Родитель дожидается результата: `delegate` — синхронный инструмент, ответ
дочернего рана возвращается модели как результат tool-вызова.

### Ребёнок работает только со своими правами

Конфигурация дочернего рана разрешается из определения дочернего агента:
модель, скомпилированный системный промт, capabilities, sandbox, MCP-серверы,
skills. Родитель **не может** ни расширить права ребёнка, ни передать ему свои:
enforcement жёсткий, на уровне инструментария, а не промта
(docs/evaluable-agent.md §6, plan §4.1).

### Делегирование — это capability, по умолчанию выключенная

В `AgentCapabilities` появляется поле `delegation`. В отличие от остальных
capabilities (nil = разрешено), делегирование по умолчанию **запрещено**:
nil или false → инструмент `delegate` не рекламируется и отклоняется.
Включает его только человек явным переключателем в карточке агента.

### Глубина ограничена

`DelegationDepth` рана: 0 у обычного запуска, +1 на каждый уровень.
Цепочка длиннее `MaxDelegationDepth` (2) отклоняется: агент на предельной
глубине обязан выполнить работу сам. Это защита и от циклов, и от «передач
по кругу».

### Причинность фиксируется в журнале

Родитель эмитит `delegation.started / completed / failed` c `child_run_id`.
Дочерний ран стартует с `parent_run_id / parent_frame_id / parent_event_id`,
поэтому событийная цепочка непрерывна: из ответа агента можно провалиться
в delegating-событие, из него — в полную траекторию дочернего рана.

### Отмена распространяется вниз

Отмена родительского рана отменяет дочерние (Temporal child workflow
cancellation). Остановка чата останавливает и делегированные работы.

### Ошибка ребёнка не роняет родителя

Если дочерний ран упал, родитель получает результат tool-вызова с описанием
ошибки и предупреждением о неопределённости эффектов — и продолжает работу
сам. `delegation.failed` фиксирует неудачу в журнале.

### Бюджеты

`max_turns` дочернего рана: по умолчанию 8, максимум 16 (аргумент инструмента).
Делегированные запуски не расходуют дневную квоту проекта — они часть
родительского рана.

## 3. Инструмент `delegate`

```
delegate(agent_id, prompt, max_turns?)
```

* `agent_id` — идентификатор агента из workspace (обязателен). Агент должен
  существовать и быть доступен в проекте (глобальный или привязанный к проекту).
* `prompt` — самодостаточная формулировка подзадачи (обязателен). В неё
  передаётся всё, что ребёнку нужно знать: родитель не может «дописать» ему
  права или системный промт.
* `max_turns` — бюджет ходов ребёнка, 1–16, по умолчанию 8.

Результат инструмента — статус, идентификатор дочернего рана и его финальный
ответ (ограниченный по объёму).

Отклонения (невалидные аргументы, лимит глубины, неизвестный агент) происходят
до запуска дочернего рана и не создают эффектов: `effect=none`.

---

## 4. Разрешение дочерней конфигурации

Workflow не ходит в БД. Конфигурация ребёнка разрешается активностью
`kernel.resolve_agent`, которая вызывает workspace API:

```
GET /v1/workspace/agents/{id}/run-config?project={project}
```

Эндпоинт возвращает `RunInput`, собранный тем же кодом, что и запуск рана
вручную: `applyAgentConfig` (промт по определению, enforcement capabilities,
skills, MCP) + `applyProjectModel`. Требуется роль writer и принадлежность
агента проекту. Этим гарантируется одна кодовая точку правды для запуска
«вручную» и «через делегирование».

Активность дополнительно вызывает `PrepareRun` (инструменты, sandbox-путь) и
отклоняет `delegate` в конфигурации ребёнка, находящегося на предельной
глубине.

## 5. События

| Событие | Где | Данные |
|---|---|---|
| `tool.started / completed / failed` | родитель | обычная семантика tool-вызова |
| `delegation.started` | родитель | `child_run_id`, `agent_id`, `ordinal`, `depth` |
| `delegation.completed` | родитель | `child_run_id`, `agent_id`, `child_status`, `turns` |
| `delegation.failed` | родитель | `child_run_id`, `agent_id`, `error_type` |
| `run.* / turn.* / model.* / tool.*` | ребёнок | обычная траектория, с `parent_run_id` и `parent_event_id` |

Идентификатор дочернего рана: `<parent-run-id>/delegate/<NN>` — стабильный,
читаемый в журнале. Workflow ID дочернего рана вычисляется той же функцией
`agent.WorkflowID(sourceID, project, runID)`, что и для обычных запусков.

---

## 6. Ограничения (зафиксировано осознанно)

* Дочерние раны не создают строк в списке Runs: они наблюдаемы через журнал
  (timeline, `parent_run_id`), но не через таблицу запусков. Отдельный вид
  «дерево рана» — Phase 2.
* Approvals дочернего рана разрешаются его собственной политикой и каналом
  одобрения; родитель не может одобрить за ребёнка.
* Сырые запуски через `POST /v1/agent/runs` (без агента workspace) могут
делегировать: это привилегированный путь с ролью writer, capability-гейт
применяется к запускам агентов workspace.

---

## 7. UI

* Карточка агента → Capabilities: отдельный переключатель
  «Делегировать другим агентам» (инвертированная семантика: выключен по
  умолчанию).
* В чате `delegate` отображается как обычный tool call; специальный виджет
  с деревом делегирования — Phase 2.
* Builtin-агенты поставляются без делегирования; пользователь включает его
  сам, если хочет строить команды.

---

## 8. План реализации

1. **Модель**: `AgentCapabilities.Delegation *bool` (`delegation`, nil = запрещено).
2. **Ядро**: `RunInput.DelegationDepth`, `MaxDelegationDepth=2`, инструмент
   `delegate` в `KernelTools`, ветка в tool-loop workflow, активность
   `kernel.resolve_agent`, `agent.WorkflowID`.
3. **Workspace API**: `GET /agents/{id}/run-config`, запрет `delegate`
   в `applyAgentConfig` при выключенной capability.
4. **Тесты**: workflow-тест делегирования (события, результат, parent-ссылки),
   тест лимита глубины.
5. **UI**: переключатель capabilities + локализация.
6. **Live-проверка**: включить делегирование агенту, делегировать из чата.

## 9. Критерии готовности

* Агент с выключенной capability не видит `delegate`; с включённой —
  делегирует, получает ответ, в журнале видна полная цепочка
  `delegation.started → дочерняя траектория → delegation.completed`.
* Глубина 3 блокируется, родитель получает понятное сообщение и продолжает.
* Отмена чата останавливает дочерние раны.
* Ребёнок не получает инструментов, отключённых его определением, независимо
  от прав родителя.
