# Саги: явная регистрация долгой работы (Sagas)

## 1. Цель

Сделать **сагу** — продолжительное усилие, которое живёт дольше одного рана и
может переходить между агентами, — явной сущностью с явной регистрацией, а не
скрытой группировкой по `task_id`.

Первоначальная реализация бюджета (`kernel/cost`) называла сагой каждую задачу:
события группировались по `ev.Context.Task`, и любые раны одной задачи
складывались в «сагу» автоматически. Это давало сумму затрат, но не отвечало на
главный вопрос: **какая работа считается одним целым**, когда её ведут разные
люди и агенты. Продолжение беседы в чате, делегирование, перехват задачи лидом
у аналитика — всё это одна работа с общей стоимостью, и решение о том, что она
едина, должен принимать агент, а не эвристика группировки.

Ключевые принципы:

* **Сага регистрируется явно.** Инструмент `saga_register` создаёт сагу и
  привязывает к ней текущую задачу. Никаких неявных саг больше не возникает.
* **Привязка живёт на уровне задачи.** Сага привязывается к `task_id`, а не к
  рану: продолжения беседы (новые раны той же задачи) и делегированные дети
  (наследуют `TaskID` корня) попадают в сагу автоматически.
* **События — единственное состояние.** Саги существуют только как journal
  события `saga.registered` / `saga.attached`; проекция строится при чтении.
  Ни одной новой таблицы, ни одного CRUD — консистентно с моделью knowledge.

---

## 2. Модель

```
Saga (явная регистрация)
 └── Task 1 ── раны (продолжения чата, retry)
 │            └── делегированные дети (delegate/plan, наследуют TaskID)
 └── Task 2 ── раны (задача лида, присоединилась через saga_attach)
```

* **Saga** — именованное усилие: `saga_id`, `title`, `goal`, автор
  (ран, зарегистрировавший сагу), время регистрации. Идентификатор
  детерминирован: `saga-<slug(title)>-<hash6(task_id)>` — повторная
  регистрация после потерянного ответа попадает в тот же `saga_id`.
* **Task** — основная единица привязки. У задачи не больше одной активной
  саги: последнее событие привязки выигрывает (последовательные
  `registered`/`attached` сортируются по времени, а не по порядку прибытия).
* **Run** — прежняя единица исполнения; ничего не меняется.

Задачи без саги никуда не исчезают: они сворачиваются в отдельный список
«задачи без саги» на странице обзора проекта. Сага не обязана быть у каждой
задачи — только у работы, которую агент считает продолжительной или
сквозной.

## 3. Инструменты агента

| Инструмент | Что делает | Идемпотентность |
|---|---|---|
| `saga_register(title, goal?)` | Регистрирует сагу и привязывает текущую задачу | Повторный вызов для уже привязанной задачи возвращает существующую сагу без новой эмиссии |
| `saga_attach(saga_id, note?)` | Привязывает текущую задачу к существующей саге | Повторная привязка к той же саге возвращает `already_attached`; привязка к другой саге переносит задачу (последний выигрывает) |
| `saga_list()` | Список саг проекта: id, title, goal, задачи, время | Чтение |

Требования к вызову: у рана должны быть `Project` и `TaskID` — иначе понятная
ошибка («этот ран без задачи, привязывать нечего»).

`saga_attach` проверяет, что сага зарегистрирована в этом проекте (по journal),
иначе отказ с подсказкой вызвать `saga_list` — защита от фантомных привязок по
опечатке в id.

Классификация инструментов:

* `saga_list` — read-only (журнальное чтение);
* `saga_register` / `saga_attach` — policy-safe записи в observation-слой
  (как `remember`): не касаются воркспейса и внешних систем, approval не
  требуется.

---

## 4. События

| Тип | Data | Context |
|---|---|---|
| `saga.registered` | `saga_id`, `title`, `goal?`, `origin=agent-tool` | Project, Run, Task, Actor |
| `saga.attached` | `saga_id`, `task_id`, `note?` | Project, Run, Task, Actor |

EventID включает `UnixNano` (`<run>/<type>/<nano>`) — повторные эмиссии после
ретрая активности не коллайдят. Дубликаты безопасны по смыслу: проекция
сворачивает их по `saga_id`/`task_id`.

Эмиссия идёт через durable outbox из activity (как `skill.proposed`), а не из
workflow-потока: тул выполняется в `ActivityRunTool`.

## 5. Распространение саги

* **Продолжение беседы.** Продолжение создаёт новый ран той же задачи — сага
  наследуется через `task_id` без каких-либо действий.
* **Делегирование.** `delegate` и `plan` копируют `TaskID` корня в ребёнка
  (kernel `ResolveAgent`), поэтому всё дерево делегирований уже внутри саги.
* **Кросс-агентский перехват (takeover).** Аналитик зарегистрировал сагу;
  лид берёт работу — его задача присоединяется через `saga_attach(saga_id)`.
  `saga_id` лид находит через `saga_list`. Дальше затраты обеих задач
  суммируются в одной саге.

Ничего из этого не требует новых механизмов распространения: сага ездит на
задаче, задача — на ранах и делегациях.

## 6. Агрегация (kernel/cost)

`ProjectBudget` теперь содержит три уровня:

* **Тоталы проекта** — сумма по всем задачам (привязанным и нет).
* `sagas[]` — по строке на каждую зарегистрированную сагу: мета (title, goal,
  автор, время), `task_ids` (хронологически), суммарные раны/агенты/токены/
  стоимость/approvals. Зарегистрированная сага без событий тоже показывается
  (нулевые тоталы) — регистрация сама по себе факт.
* `tasks[]` — по строке на задачу: те же тоталы плюс `saga_id`, если задача
  привязана.

Алгоритм агрегации двухпроходный и устойчив к порядку событий:

1. Проход по `saga.*` событиям строит мету саг и карту task→saga (последняя по
   времени привязка выигрывает; привязка к неизвестной саге игнорируется).
2. Проход по остальным событиям накапливает задачу в её собственный
   аккумулятор и, если задача привязана, — параллельно в аккумулятор саги.

`SagaCount` сменил смысл с «число задач» на «число явных саг»; `TaskCount` —
новое поле. Пер-рановый `/v1/agent/cost/task` не изменился.

Детерминизм: сортировки саг и задач — по времени начала (новые сверху),
tie-break по идентификатору; внутри саги задачи упорядочены по времени старта.

## 7. UI

Вкладка **Саги** дашборда (`/dashboard`, рядом с «Запусками»):

* тоталы проекта: задачи, саги, раны, elapsed/active, токены, стоимость,
  approvals;
* таблица саг с раскрыванием в привязанные задачи;
* таблица «Задачи без саги».

Из вкладки Runs секция саг убрана: раны — исполнение, саги — учёт. Пер-рановый
budget-вью (`Task budget` по выбранному рану) остался в Runs без изменений.

## 8. Что сознательно не сделано

* **Закрытие саг** (`saga.close`). Сага без активности естественным образом
  «остывает» (running=0, последний ран давно). Явное закрытие имеет смысл
  ввести, когда появится вопрос «какие саги вообще живы» на сотнях саг.
* **Ручное управление сагами из UI.** Сначала посмотреть, как агенты
  пользуются турами; ручная коррекция привязок — следующий шаг.
* **Саги между проектами.** Привязка проверяется в рамках одного проекта;
  кросс-проектные усилия требуют другой модели владения.

## 9. Открытые вопросы

* Стоит ли авто-предлагать `saga_register` агенту при длинных задачах
  (например, при N-м продолжении беседы) — и в каком месте системного промпта?
* Нужен ли поиск/фильтр саг на странице обзора при большом их количестве?
* Как показывать саги, у которых все задачи давно завершились, но сага не
  закрыта — «stale»-индикатор по порогу неактивности?
