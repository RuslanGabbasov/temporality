# AML Experiment 3 — Real Harness Integration: отчёт

Дата: 2026-09-19
Датасет: `benchmarks/aml3/` (финальный прогон run 4)
Артефакты итераций: `benchmarks/aml3-run1-exitmask/`, `benchmarks/aml3-run2-taskid-collision/`, `benchmarks/aml3-run3-extract-gating/` (JSONL + pg_dump памяти каждого прогона)

---

## 1. Executive summary

Адаптивный memory-слой (AML sidecar) подключён к реальному coding-циклу поверх реального
репозитория (bleve, ~800 файлов) без изменения harness-цикла. На финальном прогоне:

- **3A (стабильный репозиторий, 4 сессии × 10 задач × 2 arm):** arm D (memory) дешевле контроля
  по медиане токенов на **24%** (4474 vs 5893), по сумме токенов на **24.4%**, тестовых вызовов на
  **26%** (42 vs 57), wall-clock на **18%**. Reuse растёт от сессии к сессии (0→9→11→11).
- **3B (эволюция репозитория):** медиана токенов D ниже на **50%** (5138 vs 10184). Сценарий
  противоречия отработал полностью: устаревшая память переиспользована → опровергнута (test-fail) →
  ослаблена → вытеснена из инжекций новыми правильными памятями.
- **3C (конфликт контекстов):** **нулевая кросс-контекстная утечка** — main-задачи получили только
  main-память, legacy-задача только legacy-память. D решил 3/4, контроль 1/2.
- Качество решения не ухудшилось: успех D vs A — 3a: 21/40 vs 23/40 (шум compliance), 3b: 4/6 vs 5/6,
  3c: 3/4 vs 1/2.

Вердикт по §21: **PASS с оговорками** (см. §12). Главный качественный результат: цикл
`experience → memory → activation → reuse → outcome → reinforce/weaken` работает на реальной
траектории coding-агента, включая подавление устаревшей памяти после реального изменения репозитория.

В ходе эксперимента найдены и исправлены **три дефекта измерительного конвейера** (не памяти):
маскировка exit-кода пайплайнами, коллизия task_id в 3C, гейтинг экстракции на успех задачи.
Каждый задокументирован с evidence (§5).

## 2. Hypothesis / главный вопрос

> Если агент уже сталкивался с проблемой X и получил рабочее решение, сможет ли внешняя memory
> layer вернуть это решение перед повторным столкновением с X? Перестанет ли она навязывать
> решение после изменения репозитория? Происходит ли это без изменения reasoning-loop харнесса?

Измерительный фокус — **Repeated Discovery Avoidance** (§10 ТЗ): сколько лишних действий/токенов
агент тратит, пока находит уже известное решение; и **Memory Recovery Cost** после эволюции.

## 3. Experimental setup

- **Harness:** собственный минимальный coding-loop (`aml/harness.Runner`): model-step → tool calls
  (shell / read_file / list_files / grep) → результаты → ответ. Цикл не знает о памяти; hints
  приходят только через HTTP-хуки.
- **Sidecar:** `cmd/aml-sidecar`, контракт §4 ТЗ (`/task/start`, `/tool/before`, `/tool/after`,
  `/task/end`), PostgreSQL-стор, per-task Layer. Arm D = полный конфиг (inject at task start,
  pre-action activation, temporal ranking, guardrail, feedback).
- **Repository:** bleve v2.6.1 @ `048761396d42661336db8caa0bed1e98cf2aeaa6`, пиннутый клон
  `~/Projects/temporality-bench/repos/bleve`, офлайн-сборка (GOPROXY=off). Реальные ловушки macOS
  в игре (`grep -P`, `find -printf` фейлятся).
- **Задачи:** 10 задач на чтение/исследование подсистем (analysis, mapping, document, fusion,
  search/scorer, scorch, upsidedown, geo, numeric, registry) + тест-команда как маркер успеха.
- **Фазы:** 3A — 4 сессии без изменений репо; 3B — эволюция (TestMain-guard: тесты analysis
  требуют `BLEVE_ANALYSIS_TESTMODE=1`); 3C — та же задача на ветках main (эволюционировавшая) и
  legacy (база), 2 повтора.
- **Arms:** A (контроль, без памяти) и D (adaptive memory). Обе проходят одни задачи в одной
  сессии, барьер между сессиями.
- **Model/provider:** `deepseek/deepseek-v4.1-flash` через OpenRouter (параметры — `.env`),
  одинакова для обоих arm; max_steps 14, timeout 300s/shell, parallel 2.

Метрики на JSONL per-run: success, steps, tool_calls, failed_calls, discovery_calls (вызовы до
первого успешного `go test`), test_calls, files/unique/repeated reads, tokens, wall; lifecycle
из БД: RECALLED/INJECTED/ACKNOWLEDGED/REUSED/VALIDATED/CONTRADICTED/REINFORCED/WEAKENED.

## 4. Fixture: эволюция и ветки

- 3A: все воркспейсы на base main (без guard) — plain `go test ./analysis/` проходит.
- 3B/3C main: коммит `ci: analysis tests require BLEVE_ANALYSIS_TESTMODE=1`
  (`analysis/testconvention_test.go`, TestMain, exit 1 без env). Старая память «tests pass with
  plain go test» обязана опровергнуться, новая («нужен env var») — созреть.
- 3C legacy: ветка от BaseSHA без guard; environment-тег памяти = имя ветки.

## 5. Итерации: три дефекта конвейера (найдены анализом, исправлены, прогон повторён)

Каждый прогон ~8 минут / 98 юнитов, поэтому дефекты исправлялись с полным рерунком.

### Run 1 — маскировка exit-кода пайплайнами (`aml3-run1-exitmask`)

**Факт:** все shell-вызовы `ok=t`, включая `go test ./analysis/...` на эволюционированном main;
`CONTRADICTED = 0` за весь прогон; создан ассет-ложь «tests for analysis pass with: go test …
| tail -30; echo "exit: ${PIPESTATUS[0]}"» с conf 0.67 и cc=3.
**Причина (воспроизведена вручную):** `go test … | tail; echo …` — exit-код шелла равен коду
последней команды (`echo` → 0). Фейл замаскирован, атрибуция не срабатывает, замаскированный
«успех» экстрактится и валидируется.
**Поведение:** в 3C отравленный ассет инжектился, модель видела FAIL в выводе при exit 0,
металась — самый дорогой прогон (35.5k токенов, 8 тестовых вызовов).
**Фикс:** для команд go-тулчейна при ok по exit-коду причина доопределяется по маркерам вывода
(`FAIL`, build-паттерны) — `env.go`, тест `TestShellMasksGoTestFailure`.

### Run 2 — коллизия task_id в 3C (`aml3-run2-taskid-collision`)

**Факт:** в 3C legacy- и main-прогоны одной задачи имели одинаковый task_id и шли параллельно;
sidecar ключует состояние задачи по task_id → второй TaskStart затирал первый; у main-прогона
`injected=0` в JSONL при 3 INJECTED в БД; в `aml_tool_calls` 4 shell-вызова из 7 фактических.
**Фикс:** task_id в 3C уникален per branch (`…-r1-main` / `…-r1-legacy`) — `main.go`.
Данные 3A/3B run 2 валидны (task_id уникальны), 3C — contaminated, не используются.

### Run 3 — гейтинг экстракции на успех задачи (`aml3-run3-extract-gating`)

**Факт:** за всю 3A не создано ни одного analysis/scorch-ассета: T1 и T7 фейлились по compliance
во всех 4 сессиях (ответ верный, точный маркер-команда не названа), а экстрактор при
`!opt.Success` выбрасывал весь опыт задачи — включая реально успешные `go test`-вызовы.
Матурация получала систематический bias: память копилась только у задач с «удобными» маркерами.
**Фикс:** command-опыт (workaround, test-command) извлекается из любой задачи — их evidence
валиден сам по себе; navigation по-прежнему требует успеха задачи (§18.3-логика «what-worked»
сохранена) — `extract.go`, тест `TestCodingExtractorComplianceFailure`.

После каждого фикса — `go build` + `go test ./aml/...` зелёные, полный рерунк.

## 7. Memory reuse analysis (lifecycle)

События финального прогона: EXTRACT 73, RECALLED 48, INJECTED 69, ACKNOWLEDGED 52,
**REUSED 46, VALIDATED 45, REINFORCED 45, CONTRADICTED 1, WEAKENED 1**.

- Конверсия INJECTED→REUSED ≈ 67%: подсказки не игнорируются (risk 5 §18 не реализовался).
- Ни одного ложного валидирования после фикса exit-маскировки (VALIDATED всегда следует за
  реально ok-вызовом).
- **Memory-to-Action Latency:** по 12 задачам с reuse среднее 11.2s, максимум 86.7s —
  преимущественно «immediate/delayed reuse», «ignored» не наблюдалось.
- Зрелость (evidence diversity по сессиям): mapping 0.78 (cc до 6), analysis plain 0.55 (cc=5),
  registry 0.78, env-var новичок 0.40 → 0.57. Лестница §18.3 видна на реальных данных.

## 8. Attention / render analysis

Ранкинг (rank.go): scope 0.40, similarity 0.25, confidence 0.15, temporal 0.20, порог 0.35,
максимум 3 подсказки на TaskStart. Наблюдения:

- Порог и top-3 ведут себя как эффективный фильтр от context pollution: за прогон ни одного
  случая «3 нерелевантных подсказки»; в 3b-D-s5 T1 при живом сторе инжекций не было (все кандидаты
  ниже порога) — и это спасло задачу от ложного старта.
- Слабое место (наблюдение run 3, до фикса экстракции): при пустом сторе подсистемы кандидаты
  били score-порог из других подсистем с conf 0.71+ (scope_match 0, score ~0.27 — ниже порога,
  не инжектились). Система корректно предпочла «ничего не подсказывать».
- Известный дефект ранкинга: similarity (Jaccard) слабо отличает подсистемы — решение держится
  на scope_match и environment-разделении. Для больших lexicon нужен семантический первый фильтр
  (§3 pivot-дока) сильнее токен-пересечения.

## 9. Repeated-read analysis

`files_read ≈ 0–1`, `repeated_reads = 0` почти во всех прогонах: задачи короткие (3–6 шагов),
модель не перечитывает файлы в обоих arm. Метрика не дискриминативна на этом fixture — честно
фиксируем, что эффект repeated-discovery здесь переносится на test_calls/discovery_calls, а не
на повторные чтения.

## 10. Failure cases

1. **Compliance-фейлы** (~40–50% неуспехов обоих arm): модель даёт верный ответ без точного
   маркера-команды. Оба arm страдают симметрично; после фикса экстракции перестал выжигать память.
2. **Run 1: отравление памяти маскированным успехом** — единственный случай «память активно
   вредит» за все 4 прогона, и причиной был дефект атрибуции, а не механизм памяти (§5.1).
3. **Workaround-ассет избежал противоречия** (run 2): команда, неверная на новом main, хранилась
   под другим kind/dedup и не матчилась при противоречии test-command-ассетов. В run 4 не
   воспроизведось (workaround-ассеты, созданные после эволюции, корректно описывают fail→fix).
   Остался как известная дыра атрибуции: matching по dedup-key, а не по семантике команды.
4. **Ослабленный, но ACTIVE ассет** (conf 0.55 при ck=1): не STALE после одного противоречия —
   сглаживание не даёт одному фейлу убить память с cc=5. Инъекций после — не было (вытеснен
   ранкингом). Поведение признано корректным, но требует наблюдения на более длинной дистанции.

## 11. Useful / ignored / harmful memory

- **Полезная:** test-команды подсистем (mapping 0.78, registry 0.78, analysis env-var),
  workaround «plain go test fails → use env var» (0.78), navigation на файл ответа (0.78).
  Именно они дали −24…−50% токенов и −26% тестовых вызовов.
- **Игнорируемая:** не зафиксирована (INJECTED→REUSED 67%, latency низкая).
- **Вредная:** один кейс в run 1 (дефект атрибуции, §5.1); после фиксов вредных инжекций нет.

(в) одна модель, короткие задачи, n мал в 3B/3C.

## 13. Conclusions (факт / поведение / интерпретация — раздельно)

**Измеренный факт.** На фикстуре bleve при прочих равных: медианные токены warm-агента ниже на
24% (стабильный репо) и 50% (после эволюции); тестовых вызовов меньше на 26–31%; reuse растёт по
сессиям; кросс-контекстных инжекций 0; противоречие→ослабление→вытеснение наблюдается ровно там,
где репозиторий реально изменился.

**Наблюдаемое поведение.** Модель охотно использует подсказки (67% инъекций → reuse, латентность
секунды); при пустом сторе система молчит вместо шума; после эволюции агент с памятью платит один
фейл и сразу переходит к новому решению.

**Интерпретация.** Ценность внешней memory-layer на реальной траектории подтверждается не «умом»,
а экономией: агент перестаёт повторять уже оплаченное исследование. Экономия концентрируется там,
где прошлый опыт переносим (команды, конвенции, навигация), и исчезает там, где задача не
оставила валидируемого опыта.

**Гипотеза (не доказана).** На более длинных задачах (десятки шагов) эффект будет больше за счёт
повторных чтений и повторных гипотез, которых короткие задачи не порождают; масштабирование
lexicon потребует семантического retrieval сильнее Jaccard.

## 14. Next experiment

1. **Длинные задачи** (bug-fix с локализацией на 20–40 шагов): проверить, переносится ли эффект
   на discovery-домен (повторные чтения, отвергнутые гипотезы) — главный ожидаемый выигрыш AML.
2. **STALE-дожим:** сценарий с несколькими противоречиями/низким cc у старой памяти и проверкой
   resurrection (§18.2), пока не упражнён на реальных данных.
3. **Typed contradiction (§18.1)** в coding-мире: value/type/shape mismatch при read/grep —
   закодировать и прогнать.
4. **Вторая модель** (memory compliance): сокращённый 3A-сценарий, INJECTED→REUSED/IGNORED.
5. **Дедуп-нормализация команд** (cosmetic-суффиксы `| tail -N`, `; echo` плодят варианты) и
   **семантический pre-filter** перед rank.
6. Подключение второго harness-типа (не coding) без изменения sidecar — проверка контракта.
