## 1. Executive summary

Проведён контролируемый эксперимент по ТЗ `temporality-pivot-tz.md` §15–19: 3 независимые пары, в каждой — A-fresh (строит память) → B-cold / C-warm-facts / D-warm-investigation на одной и той же task-2 фикстуре.

**Прогон 1 (до фикса): NEGATIVE (memory hygiene failure).**

- Экономический gate (`warm ≤ 0.7 × fresh`) не пройден: среди успешных прогонов C = 0.73–0.93× B, D = 0.87–1.09× B.
- Качество **ухудшилось**: B-cold 3/3 success, C-warm-facts **1/3**, D-warm-inv **2/3**.
- Все 3 провала warm-плечей — один и тот же режим: **false completion из стейл-памяти** (1 шаг, 0 действий, «уже исправлено, тесты зелёные»).
- Корневая причина найдена и задокументирована (§8): итоговые claims эпизода A («финальный `go test` зелёный», confidence=1) повышаются до `scope=world, state=confirmed` **без привязки к версии мира** и рендерятся новому эпизоду как текущие факты. Модель ведёт себя рационально — она отказывается делать уже «сделанную» работу.
- Память при этом **доставляется и меняет поведение**: D читал 2 файла против 4–6 у B (навигация по памяти/grep), в p3 D эхо-переиспользовал 3 claim'а. Т.е. pipeline memory → render → attention → cognition работает; сломана **гигиена и временная валидность** памяти, а не механизм доставки.

Вердикт по §24 (главный критерий): не достигнут — warm-агент дешевле только в отдельных прогонах и ненадёжнее.

## 2. Гипотеза

> Накопленная память FRP (факты + история исследования) делает следующую независимую задачу в том же мире дешевле (токены/шаги/чтения) без потери качества.

## 5. Наблюдение: полезная память

- **Навигация**: D во всех успешных прогонах читал 2 файла (B: 4–6). В p1/p3 D использовал `run_command` (grep) по подсказкам из памяти вместо слепого чтения.
- **Эхо-переиспользование**: p3 D — 3 claim'а в эмиссии дословно опираются на память.
- **Цена**: p3 C = 0.73× B — почти экономический gate; p3 D = 0.87× B. В p3 у D prompt оказался меньше, чем у B (74 236 vs 90 628) — меньше чтений → тоньше recent-секция.
- C в p3 refuted_revisits = 0: refuted-история не понадобилась (задача 2 не пересекалась с закрытыми путями задачи 1).

## 6. Наблюдение: harmful memory (все 3 провала)

Единый режим failure (C p1, C p2, D p2):

- 1 cognitive step, 0 actions, 0 read_file, 0 run_tests;
- completion объявляет задачу выполненной, описывая **баги задачи 1** и их исправления;
- в тексте completion фигурирует «итоговый прогон `go test ./...` зелёный (exit_code 0)», **которого в этом эпизоде не было** — модель галлюцинирует верификацию, опираясь на память;
- checker: `go test ./...` — FAIL (в мире лежат баги task 2).

Точная цитата (D, pair 2, reasoning):

> «Память мира содержит подтверждённые факты: обе причины падений локализованы и устранены в исходном коде… итоговый прогон тестов дал exit_code 0.»

Форензика сохранена: `benchmarks/forensics/run2-c-emission.json`, `benchmarks/forensics/run2-d-render.json`; БД переименованы в `frp_forensics_run2_{a,b,c,d}`.

## 7. Интерпретация: механизм отравления

Render-packet D (pair 2) содержит в `world_memory`:

```json
{"state": "confirmed", "confidence": 1, "scope": "world",
 "proposition": "Финальный запуск `go test ./...` в репозитории завершился успешно: exit_code 0, все пакеты с тестами выдали ok."}
```

Плюс confirmed-клеймы о багах task 1 («Remove не удаляет запись…»), которые в текущем мире (world_version=2, баги task 2) также **ложны** — фиксы A реально применены в workspace.

Три архитектурных дефекта (в терминах pivot TZ):

1. **§11 (правило качества памяти) не реализовано**: execution-outcome («тесты зелёные», «баги устранены») — это *episode experience*, а не world knowledge, но он повышается до `scope=world, state=confirmed, confidence=1`.
2. **§21 (версионирование) не реализовано**: claims не несут world_version; render не маркирует стейл. `episode.started` нового эпизода знает `world_version: 2`, но память не сопоставляется с ним.
3. Нет защитного инварианта «completion требует верификации в текущем эпизоде», когда в памяти есть outcome-утверждения.

Провал стохастичен по содержанию памяти A (p2 A закончил за 3 шага и оставил «ядовитый» outcome-клейм; p3 A — нет), поэтому warm-надёжность = 33–67% вместо 0/100%.

## 9. Что работает (не выбрасывать)

- Механизм доставки memory → render → attention → cognition подтверждён метриками (delivered 5–15, echo, ops_on_mem).
- Сокращение discovery: reads 2 vs 4–6 у D во всех успехах.
- Branch-visibility фикс сделал cognition зрячим к выводу тестов (A больше не спиралит; 3/3 success).
- Драйвер `scripts/memory_benchmark.py` воспроизводим и даёт полные per-run метрики (dump'ы: `benchmarks/pivot-p{1,2,3}.json`).

## 10. Следующий эксперимент (минимальный, без нового M17)

1. **Hygiene**: классифицировать claims при повышении в world-scope — outcome-утверждения («тесты зелёные», «исправлено») остаются episode experience (§11), не подтверждёнными world facts.
2. **Версионирование**: claims получают `world_version` наблюдения; render маркирует `stale` при несовпадении с текущей версией мира (§21) — или фильтрует.
3. (Опционально) policy-guardrail: completion без единой верификации (`run_tests`) в текущем эпизоде при наличии outcome-memory отклоняется с требованием проверить.
4. Повторить те же 3 пары тем же драйвером. Ожидание: false-completion исчезает; тогда увидим истинную экономику warm-памяти (по p3 — потенциал ~0.73×).

Не делать (§13 старого ТЗ сохраняется): новый storage, Neo4j, vector DB, новый протокол, rewrite render.

## 11. Академическая честность

- Tokens — по usage провайдера, агрегированы драйвером; wall-clock включает латентность модели.
- Медианы по n=1–3 — разведывательные, не статистические.
- Deterministic replay (AC7) в этой сессии отдельно не перепроверялся (проверялся на этапах 1–5).
- A варьирует (3–5 шагов, 62–104K токенов) → содержание памяти A варьирует → warm-результаты content-dependent; это само по себе finding: **надёжность warm-агента производна от гигиены памяти builder'а**.

# Прогон 2 — после фикса гигиены памяти (pivot §11/§21)

## 12. Фикс

По итогам NEGATIVE-вердикта реализован минимальный фикс (без нового M17, без миграций схемы):

1. **Штамп версии мира**: все lifecycle-события клеймов (`claim.candidate/supported/refuted/superseded`) теперь несут `payload.world_version` — в `runtime/step/step.go` (эмиссии модели, `input.WorldVersion`) и `ingest/ingest.go` (бутстрап, `r.World.StateVersion`).
2. **Вывод версии клейма**: `ListClaimsByWorld` (postgres + memory) вычисляет `claim.WorldVersion = max(world_version по lifecycle-событиям)` — без записи в claims-таблицу, версия живёт в событийном логе (replay-консистентность). Подтверждение (confirm) в новом мире обновляет «свежесть» клейма до его версии.
3. **Маркировка stale в рендере**: `worldMemoryItems` получает текущую версию мира через `GetWorld`; клеймы с `0 < WorldVersion < текущей` рендерятся с `"stale": true, "world_version": N` + note «earned against world state vN; the world is now vM — treat as history and re-verify before relying on it». Действует в обоих режимах (confirmed и полный).
4. Регрессионные тесты: `frp/render/world_stale_test.go` (механизм end-to-end на memory-сторе); проверено на postgres-интеграции (`TestWorldScopedClaimBase`, полный набор миграций).

Проверка в реальном прогоне: render-packet первого шага C содержит все 8 клеймов A с `stale:true, world_version:1`, включая оба ядовитых («после правок… go test зелёный», «применённые правки…»). БД: `frp_stalefix_p1_*`.

## 14. Наблюдение и интерпретация прогона 2

- **Наблюдение**: false-completion исчез полностью; warm-агенты начинают с run_tests/чтений и работают с миром заново, опираясь на память как на карту, а не как на готовый ответ.
- **Наблюдение**: C сократил чтения (2–3 против 2–4 у B; в прогоне 1 было 0 у провальных) — память действительно направляет discovery. ops_on_mem (1–4) и echo (0–1) — модель активно работает с памятью: подтверждает/опровергает унаследованные клеймы.
- **Наблюдение**: шагов у warm больше (6 против 4 у B): цена проверки stale-памяти + работа с ней (ops) съедает выигрыш от сокращённого discovery.
- **Интерпретация**: на этой фикстуре (маленький репозиторий, cold-агенту нужно всего 4 шага/2 чтения) экономический потенциал warm-памяти ограничен — почти нечего экономить. Паритет D≈0.95×B при 100% надёжности — разумная база, но не актив.
- **Гипотеза**: на более крупной фикстуре (scale 20+, длинный горизонт, дорогой discovery) соотношение должно сместиться в пользу warm — доля discovery в стоимости cold-агента вырастет. Это следующий эксперимент (увеличить scale/задачу, не трогая архитектуру).
- **Попутный факт**: D (полная память с историей) ≥ C (только факты) в 2 из 3 пар (D/C = 0.75, 0.97) — после фикса слой investigation-истории больше не ядовит и слегка полезен.

1. **Фикстура побольше**: повторить прогон на scale 16–24 (или задаче с более дорогим discovery) — проверка гипотезы, что экономика warm-памяти проявляется при дорогом discovery. Тот же драйвер, тот же фикс.

3. **A1/A2/A3 performance rescue** отдельной веткой: cacheable render, native tool-calling, short aliases — теперь, когда рендер стал ещё чуть тяжелее (stale-поля), кэшируемость важнее.
4. Не делать: расширение контекстов, новая БД, новый протокол (§13 старого ТЗ).

## 17. Прогон 3: семь оптимизаций цикла (что было сделано)

Между прогонами 2 и 3 реализованы (без изменения схемы БД и протокола):

1. **Усечение diagnostics** (`render.boundedDiagnostics`): `error.diagnostics.stdout/stderr` в пакетах ограничены 4096 рун с маркером; полное содержимое остаётся в событийном логе. Copy-on-write — хранимое событие не мутируется.
2. **Experience/knowledge split** (`ListClaimsByWorld`, postgres + memory): клеймы, чей evidence содержит хотя бы один `world.effect`, исключаются из longitudinal-базы — это опыт эпизода («после правок тесты зелёные»), а не знание о мире. Яд из прогона 1 убран на уровне read-path, а не рендера.
3. **Relevance-ранжирование world_memory**: внутри групп confirmed/hypothesis — лексическое перекрытие proposition с objective+focus (детерминированно, replay-safe), confidence только tiebreak.
4. **Seed процедур objective** (`procedure.BuildConfig.ObjectiveText`): триггер процедуры строится из токенов affordance-id **плюс** текста objective исходного эпизода; `procedureID` не зависит от триггера (идентификаторы стабильны). Ранее триггер «read file» лексически не пересекался с русской формулировкой цели — рендерилось 0 процедур; теперь warm-пакеты несут процедуры (проверено по render_packet_raw в БД пары 3).
5. **Repair-retry эмиссий** (`model.RejectedError` + `EmitRepair` + цикл в modelstep, ≤2): отклонённая (невалидная/битая) эмиссия пере-запрашивается с точной причиной отказа и цитатой предыдущего ответа; `usage` суммируется по всем попыткам (честный учёт). HTTP/timeout/truncation-ошибки не репарятся.
6. **Запрет пустых эмиссий** (инструкция в system prompt): эмиссия обязана содержать действие или completion.
7. **Prefix-stable wire form** (render-0.6.0): секции — objective, affordances, world_memory, procedures (стабильная голова) → identity, map, focus, health, working_set, periphery, recent (волатильный хвост); волатильные поля Packet (frame_id, render_id, memory_version) сериализуются после секций. Всё для провайдерского prefix-кеша.

Все тесты зелёные (`go test ./... -count=1`, postgres-интеграция на полностью мигрированной БД). Прогоны: `benchmarks/pivot-opt-p{1,2,3}.json`, БД — `frp_pivot_p1_*` (перезаписывались, сохранились только от пари 3).

## 19. Анализ прогона 3

- **Факт**: разброс между парами резко вырос (C: 85K→220K; B: 97K→136K). При n=3 медианы неустойчивы; сравнение с прогоном 2 (B 84K → 101K) — внутри шума, тем более что часть изменений (repair-retry) делает учёт честнее: раньше токены проваленных попыток не попадали в метрики, теперь суммируются (в p1 у C было 2 драйверных ретрая + серверные repair-попытки).
- **Факт**: warm-агенты во всех парах тратят больше шагов (7 vs 5 у B). Память стала более «вовлекающей»: relevance-сортировка поднимает задачи-релевантные клеймы наверх, stale-маркировка требует перепроверки, процедуры дают готовые паттерны — и модель responds работой: подтверждает/опровергает клеймы (ops_mem до 6), перепроверяет stale-факты чтениями. В p2 это дало лучший результат за всю историю эксперимента (C=0.63×B, D=0.80×B); в p1/p3 — удорожание.
- **Факт**: D ≥ C стабильно (D/C: 0.97, 1.27, 0.45) — история исследования и refuted-пути в среднем полезнее чистых фактов.
- **Наблюдение**: лучший случай (p2) демонстрирует целевое поведение: warm-агент прочитал 2 файла против 4 у cold, прошёл 6 шагов против 5, истратив 63% бюджета cold-агента. Худший (p3 C, 9 шагов): модель ушла в длинную верификацию памяти.
- **Гипотеза (непроверена)**: инструкция «действие или completion» (оптимизация 6) на warm-агентах вынужденно сцепляет шаги-реконсиляции (claim_ops) с действиями — реконсиляция без действия запрещена, а завершать нельзя. Это может конвертировать дешёвые шаги-осознания в дорогие шаги-действия и объяснять часть +2 шагов у warm. Проверяется A/B-прогоном с смягчённой формулировкой (разрешить чистые reconcile-шаги при наличии claim_ops).
- **Интерпретация**: optimizations 1–7 снизили стоимость отдельного пакета (diagnostics, prefix-кеш — не виден в счётчике токенов, но снижает реальную цену) и качество доставки (процедуры теперь реально рендерятся), но доминанта стоимости — число шагов, и память пока что его увеличивает, а не сокращает. Gate ≤0.7× не пройден; по лестнице §10 — FAIL-паттерн «retrieved but doesn't (consistently) help».

**Вердикт по прогону 3: FAIL** (экономически), с бимодальным поведением: лучший режим (p2) проходит gate с запасом, худший (p1/p3) — противоположный. Следующее решающее движение — не новые оптимизации, а поиск условий стабильности лучшего режима (фикстура с дорогим discovery, накопительный режим, A/B инструкции).
