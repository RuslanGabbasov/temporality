# Temporality — универсальная интеграция и план реализации

## Решение

Temporality развивается как внешний слой наблюдаемости и активации знаний. Он не требует переносить агентный цикл, планировщик или выполнение инструментов в Temporality. Любой harness остаётся владельцем цикла агента; Temporality принимает события, строит временные проекции и по запросу возвращает подсказки с происхождением.

Целевая независимость означает общий протокол и ядро, которые не знают о конкретном harness. Она не означает отсутствие интеграционного кода: получение событий требует producer-интеграции, а помещение подсказки в контекст модели требует hook на стороне harness либо совместимого proxy.

```text
agent harness ── events ──▶ Temporality
      ▲                         │
      └── contextual hints ─────┘
```

Подсказка не подменяет результат инструмента. API возвращает отдельный блок контекста с provenance; интеграция решает, как передать его модели.

## Границы компонентов

### Ядро Temporality

- приём, валидация и append-only хранение нормализованных событий;
- дедупликация и временная реконструкция;
- проекции знаний, жизненного цикла, связей и provenance;
- ручная инвалидация и правила автоматического выявления конфликтов/устаревания;
- поиск актуальных подсказок с объяснимыми основаниями;
- API и UI для timeline, diff, knowledge detail и истории инвалидации.

### Интеграции с harness

- отправляют события по HTTP/JSON либо через тонкий SDK;
- по возможности перехватывают завершение model/tool операций;
- при желании запрашивают подсказки и передают их в отдельном контекстном блоке;
- переводят собственные callbacks и идентификаторы в общий протокол.

Специальная поддержка FRP, GoClaw или другого harness является адаптером. Ни один такой адаптер не является обязательной частью ядра.

## Контракт наблюдаемого события

Первая версия должна быть компактной, языконезависимой и терпимой к неполным данным. Поля harness-specific хранятся в расширяемом `data`, а не превращаются в обязательные FRP сущности.

```json
{
  "schema": "temporality.event/1",
  "event_id": "source-defined-id",
  "occurred_at": "2026-09-24T10:00:00Z",
  "source": { "integration": "my-harness", "version": "1" },
  "context": {
    "project": "repo-or-project",
    "run": "run-42",
    "task": "task-7",
    "actor": { "id": "agent-a", "type": "agent" },
    "parent_event_id": "source-parent-id"
  },
  "type": "tool.completed",
  "data": { "tool": "tests", "status": "failed" },
  "evidence": []
}
```

Требуются schema, event ID, время, source, type. `context`, `data` и `evidence` могут быть частичными. При хранении фиксируется отдельное server-side время приёма. Идемпотентность задаётся парой source + event ID; повтор события не создаёт вторую запись. Внешние идентификаторы остаются строками и не требуют UUID или FRP frame/episode. `occurred_at` и server-side `received_at` сохраняют valid-time и transaction-time; запрос `as_of` ограничивает первое, `known_at` — второе.

Начальный словарь типов включает `run.started/completed`, `task.started/completed`, `model.requested/completed`, `tool.started/completed`, `knowledge.proposed/used/confirmed/challenged/corrected/invalidated/disproved`. Неизвестные не-knowledge типы принимаются и сохраняются без потери данных.

Knowledge события несут ID утверждения, proposition или ссылку на исходное событие, actor, evidence refs и контекст. Жизненный цикл — проекция событий, а не изменяемая запись со скрытой историей. Ручная и автоматическая инвалидации записываются как отдельные события с причиной и основаниями.

## Подсказки и точки подключения

API активации принимает текущую задачу/контекст и необязательные сведения о завершившемся tool call. Ответ содержит отдельные подсказки: текст или структурированные knowledge refs, состояние/актуальность, evidence, источник и причину выбора. Ответ не меняет хранимый event и не притворяется частью tool output.

Уровни интеграции:

1. **Recorder:** отправка событий; знания и подсказки доступны в UI/API.
2. **Context provider:** harness отдельно запрашивает подсказку и передаёт её модели.
3. **Tool boundary middleware:** обёртка после tool call автоматически запрашивает подсказки и возвращает harness пару `tool_result` + `temporality_context`.

Уровень 1 не требует вмешательства в control loop, если harness уже имеет callbacks/log export. Уровни 2–3 требуют точки подключения; общий протокол позволяет сделать адаптер небольшим, но не устраняет его.

## Инвалидация

Все изменения статуса являются наблюдаемыми событиями. Ручная команда указывает знание, автора и причину; автоматическое правило указывает правило/версию и evidence. Проекция сохраняет историю, причинные ссылки и распространение invalidation по явно заданным зависимостям. Автоматическое правило не удаляет и не переписывает исходное знание.

В MVP включить ручную инвалидацию и отображение истории. Автоматическую инвалидацию ограничить детерминированными, проверяемыми случаями (например, прямое опровержение связанным evidence); эвристики stale/conflict вводить после получения реальных данных и показывать как кандидатов на проверку, а не как истину.

## Сопоставление с текущим репозиторием

- Переиспользовать append-only события, временной replay, PostgreSQL, claims/evidence, claim transitions, проекции и существующую расследовательскую логику debugger там, где они не требуют FRP runtime.
- Текущий `frp/protocol.Event` и таблица `events` завязаны на `frp/0.3`, UUID и episode/branch поля. Универсальный внешний контракт должен иметь отдельную границу; адаптировать его в FRP Event без решения по внешним строковым ID и изоляции проектов нельзя.
- Текущие `/v1/step`, `/v1/model-step`, `/v1/bootstrap`, Frames, Objectives, World и Executor остаются FRP runtime интерфейсами. Они не являются универсальным ingest API.
- Текущий debugger запрашивает FRP API и предполагает episode/frame. Его data access нужно отделить до добавления Temporal Knowledge Cloud.
- README/ROADMAP и pivot-документы описывают разное продуктовое направление. Этот документ фиксирует новую границу; обязательная интеграция с GoClaw из pivot §24/§27 снимается. GoClaw может стать одним из тестовых producer-ов, только если доступен без специальных затрат.

## Этапы работ

### Этап 1 — независимый event contract и ingest

- зафиксировать JSON Schema и примеры;
- определить append/batch API, дедупликацию, ограничения payload и ответы на частичный batch;
- хранить строковые external IDs отдельно от FRP UUID сущностей;
- добавить клиентские примеры через curl, Python и JavaScript без сторонних зависимостей;
- определить безопасную политику хранения/redaction чувствительных payload.

**Выход:** произвольный harness может передать события без Frames, Objectives и UUID-идентификаторов Temporality.

### Этап 2 — универсальная история и knowledge lifecycle

- проекция project/run/task/actor и временная пагинация;
- нормализация knowledge lifecycle из общих событий;
- provenance/evidence links и запрос знания на момент времени;
- ручные confirm/challenge/correct/invalidate actions как append-only события;
- повторная сборка проекций из журнала.

**Выход:** можно восстановить, что команда знала в момент T, на основании каких событий и кто изменил статус.

### Этап 3 — наблюдаемость MVP

- UI project/run timeline;
- фильтры actor/task/type/time;
- detail знания с lifecycle, evidence и provenance;
- diff двух временных точек;
- расследование от знания до исходного события.

**Выход:** полезная история доступна даже при подключении только recorder-уровня.

### Этап 4 — API подсказок и оценка полезности

- query/activation API по задаче и tool observation;
- объяснимый ответ с freshness, статусом и evidence;
- передача результата как отдельного контекстного блока;
- запись событий `hint.offered`, `hint.used` и связанного outcome;
- сравнение поведения с подсказками и без них на одинаковых задачах.

**Выход:** проверяется гипотеза о влиянии своевременной активации прошлых знаний.

### Этап 5 — универсальные интеграционные примеры и авто-инвалидация

- проверить контракт на 2–3 разных источниках/harness через HTTP или тонкие callbacks;
- измерить объём кода, конфигурации и доступность provenance;
- добавить ограниченные детерминированные правила авто-инвалидации;
- расширять SDK/адаптеры только по выявленным повторяющимся потребностям.

**Выход:** переносимость подтверждена несколькими независимыми интеграциями, а авто-инвалидация объяснима и воспроизводима.

## Критерии успеха

1. Подключение нового источника не требует внедрять Temporality runtime или менять агентный цикл.
2. Базовая запись событий работает через простой HTTP/JSON интерфейс.
3. Строковые ID harness не требуют UUID преобразований и сохраняют исходную идентичность.
4. Knowledge detail позволяет пройти до первичного события/evidence и увидеть все lifecycle transitions.
5. Инвалидация имеет автора/правило, причину, время и evidence; история неизменяема.
6. Подсказки выдаются отдельно от результата инструмента и имеют provenance.
7. Эффект подсказок измеряется через последующие события/outcomes.

## Принятое решение по хранению

Универсальные события хранятся в отдельной append-only таблице `observation_events`; FRP `events` остаётся источником истины только для FRP runtime. Ключ идемпотентности — `(source.id, event_id)`, внешний event/run/task/actor ID остаётся текстом. Порядок задан кортежем `(occurred_at, received_at, source_id, event_id)`, cursor кодирует тот же кортеж. Проекты фильтруются до проекции; перевод внешних строковых ID в UUID не выполняется. Это сохраняет совместимость существующих FRP replay и не требует миграции старых событий.

Остаток открытого хранения для deployment уровня продукта — изоляция источников по учётной записи/tenant и политики хранения/redaction. Нынешняя HTTP API не вводит выдуманную multi-tenant модель; эти требования нужно определить до внешнего многопользовательского развёртывания.

## Текущее состояние реализации

В репозитории уже есть первая end-to-end вертикаль:

- `temporality.event/1` schema/type без FRP и с непрозрачными строковыми внешними ID;
- отдельная append-only PostgreSQL таблица и in-memory adapter;
- batch append (до 100), идемпотентность `(source.id,event_id)`, конфликт при разном повторном содержимом;
- фильтрованное чтение с opaque cursor;
- lifecycle projection `proposed/used/confirmed/challenged/corrected/superseded/invalidated`;
- explicit knowledge relations, one-hop graph hint expansion, and downstream `at_risk` propagation for `derived_from`/`depends_on` edges;
- ручная инвалидация append-only событием с actor/reason/evidence;
- детерминированная автоматическая инвалидация при явном `knowledge.disproved` с evidence (`explicit-evidence-disproof.v1`), без вывода истины из свободного текста;
- API выдачи подсказок по точным entity/topic refs и explainable lexical overlap; ответ отдельным `context_block`, запись `hint.query`/`hint.offered` для измерения использования.

Маршруты: `POST/GET /v1/observations/events`, `GET /v1/observations/knowledge?project=...`, `POST /v1/observations/knowledge/invalidate`, `POST /v1/observations/hints`. Клиентские примеры без зависимостей: `examples/python/temporality_client.py` и `examples/javascript/temporality.mjs`.

Независимый экран `/observability` уже показывает отфильтрованную по проекту временную ленту, cursor pagination, группировку знаний по topic/entity, сравнение двух временных точек, детали provenance/evidence, исходное событие и ручную инвалидацию. Встроенная форма проверяет выдачу hints на task/tool/tool result. Это рабочая вертикаль MVP, но ещё не завершённая эксплуатационная поставка: требуется проверка на реальной базе с миграцией, интеграция нескольких producer-ов, правила хранения/redaction и более качественный retrieval, если lexical baseline окажется недостаточным.

AML adapter (`aml/temporality`) проверяет протокол на отдельном Go Hooks surface внутри репозитория: пишет task/tool события, вызывает hints после результата инструмента, добавляет их отдельным сообщением и записывает `hint.used`. Связь подсказки с итогом задачи маркируется только как корреляция, не как причинность.

Текущее покрытие этапов: этап 1 реализован для HTTP/JSON, схема, curl и два тонких HTTP-клиента готовы; этап 2 реализован базовым lifecycle, временным чтением, provenance и явными отношениями; этап 3 реализован базовым UI; этап 4 реализован базовым retrieval и feedback-событиями. AML adapter проверяет контракт на отдельном hook surface внутри репозитория. Этап 5 остаётся следующим: подключить действительно независимые внешние harness, собрать реальные события и на их основании сузить автоматические правила инвалидации. `knowledge.disproved` уже даёт явный детерминированный путь авто-инвалидации, но это не заменяет оценку кандидатных правил на реальных данных.
