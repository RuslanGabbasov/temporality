# Промпт T3 — Security Auditor

Задача: аудит безопасности новой возможности «оператор редактирует полный
Dockerfile профиля песочницы» (спецификация
`docs/tasks/2026-10-21-sandbox-dockerfile-editing/spec.md`, проблема I-3).

Контекст: сборка образа идёт через docker-сокет хоста (root-эквивалентный
класс доверия), `docker build -t <tag> -` с Dockerfile из stdin, build context
отсутствует. Рецепт теперь может задавать оператор (роль writer+) целиком;
модель-мастер (LLM-черновик профиля) по контракту никогда не заполняет рецепт
(D2.2). Валидация текста: запреты ADD / COPY без --from / ONBUILD, обязателен
FROM, ≤16 KiB, UTF-8 без NUL (D3); результат сборки пинится digest-ом,
запуск песочниц — под `--pull=never` с существующим контуром изоляции
(read-only rootfs, cap-drop=ALL, no-new-privileges, pids-limit, noexec /tmp).

Проверь (по реализованному коду задач T1/T2, дифф против HEAD 223eb0a):
1. I-3: какие векторы даёт редактируемый рецепт через docker-сокет (например,
   multi-stage `COPY --from`, `RUN --mount`, обращения к сети при сборке,
   попытки влиять на хост) и достаточны ли запреты D3 + существующие
   ограничения.
2. Имплентацию D2.2: действительно ли модельный путь (билдер-мастер, любые
   model-driven поля) не может протащить `dockerfile_override`.
3. Имплементацию D3: обходы валидатора (регистр, пробельные префиксы,
   continuation `\`, комментарии, heredoc, escape-символы Dockerfile).
4. Маппинг ошибок D4 и API/preview: нет ли инъекций в логи/ответы.
5. Класс доверия: достаточно ли, что действие доступно роли writer+ и
   попадает в аудит/журнал событий.

Формат результата: вердикт по I-3 (принято/требует исправлений), список
находок: id, критичность (critical/high/medium/low/как принято в твоей
методологии), уязвимость/вектор, где в коде, рекомендация. Критические и high
находки должны содержать конкретное исправление. Ничего не изменяй в коде —
только заключение.
