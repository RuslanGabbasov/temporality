# Спецификация: полное редактирование Dockerfile в конструкторе песочниц

Дата: 2026-10-21. Автор: Lead (оркестратор). Статус: утверждена оператором
(выбран вариант B — оператор полностью владеет текстом Dockerfile).

## 1. Проблема (воспроизведено по логу оператора)

Сборка кастомного профиля песочницы падает:

```
#6 [3/3] RUN apk add --no-cache nmap nikto sqlmap python3 py3-requests openssl curl
#6 0.725 ERROR: unable to select packages:
#6 0.725 sqlmap (no such package):
```

Три корневые причины (по коду HEAD 223eb0a):

- **RC-1 («придумывает пакеты»)**: LLM-мастер профиля
  (`kernel/agent/sandboxbuilder.go`) подставляет имена пакетов, которых нет в
  индексе дистрибутива (`sqlmap` отсутствует в apk Alpine). Валидация имени —
  только синтаксическая (`kernel/sandbox/build.go` `validPackageName`) плюс
  маппинг apt↔apk-алиасов; существование пакета не проверяется нигде.
- **RC-2 (нельзя поправить руками)**: оператор управляет только полями
  `base` + `packages`; итоговый Dockerfile собирается программно
  (`CustomDefinition`, build.go:195 — конкатенация `RUN apk add …` к рецепту
  базы) и неизменяем для оператора: править нечего.
- **RC-3 (неинформативная ошибка)**: `BuildDefinition` отдаёт сырой лог
  `docker build` целиком; имя виновного пакета и причина не выделяются.

## 2. Валидация требования

### 2.1. Полнота
Исходная формулировка («править его или параметризировать дополнительно»)
содержала неоднозначность объёма. **Решено оператором 2026-10-21: вариант B —
полное редактирование Dockerfile.** Дополнительно в объём включены (согласовано
с оператором при уточнении): понятные ошибки о несуществующих пакетах (RC-3) и
защита от повторного выдумывания пакетов на уровне мастера (RC-1, промпт).

Прочие пробелы полноты закрыты явными решениями §3 (что происходит со
встроенными профилями, с закреплённым digest при правке, с моделью-мастером).

### 2.2. Логическая непротиворечивость
Зафиксировано противоречие **I-2**: принцип
`docs/sandbox-profiles.md` §4 «профили композируются на известных базах, базовые
образы не выдумываются» против выбранного полного редактирования.
Разрешение (D1): принцип уточняется — оператор (и только оператор) может
задать произвольный рецепт, включая любой `FROM`. Компенсирующий контроль не
снимается: результат сборки по-прежнему пинится `@sha256:…` и запускается под
`--pull=never`. Mutable-теги внутри редактируемого `FROM` — осознанный
trade-off оператора (фиксируется в документации).

### 2.3. Техническая реализуемость
Подтверждено по коду: сборка идёт как `docker build -t <tag> -` с Dockerfile из
stdin (`BuildDefinition`), **build context отсутствует**. Следствия, вошедшие в
D3: `COPY` без `--from` и `ADD` физически не работают (и запрещаются валидацией
с понятной ошибкой), multi-stage (`FROM … AS …`, `COPY --from=…`) работает и
является штатным сценарием. Реализуемо силами одной итерации: модель данных
(одно текстовое поле + миграция), валидатор, путь сборки, UI-редактор, тесты.

### 2.4. Явно зафиксированные проблемы
| id | Проблема | Разрешение |
|----|----------|------------|
| I-1 | Неоднозначность объёма («править ИЛИ параметризировать») | Решение оператора: вариант B, полное редактирование |
| I-2 | Противоречие с принципом «не выдумывать базы» | D1: уточнение принципа, компенсирующий контроль сохраняется |
| I-3 | Текст рецепта = произвольный код при сборке через docker-сокет хоста (root-эквивалентный класс доверия) | Принято осознанно: действие оператора с ролью writer+, модель никогда не пишет рецепт (D2.2); обязательно заключение Security Auditor (задача T4) до закрытия |
| I-4 | Инъекция в логи/ошибки (аудит F-06): сырой вывод `docker build` (mutable/внешние `FROM` = недоверенный pull-класс) вставлялся в `fmt.Errorf` без санитизации — подделка строк server-лога через `\r`, ANSI-эскейпы в терминале/`less`, разметка ошибок в UI | D8: санитизация вывода ровно один раз сразу после захвата (см. §3, D8 — что режется, лимит, точки применения) |

## 3. Решения (контракт)

- **D1. Новый режим профиля «operator recipe».** Кастомный профиль несёт
  необязательное поле `dockerfile_override` (полный текст Dockerfile). Оно
  становится единственным источником рецепта.
- **D2. Инварианты.**
  1. Ровно один источник рецепта: `base[+packages]` **XOR** `dockerfile_override`
     **XOR** внешний `image`. Установка override требует пустых `base` и
     `packages` (и наоборот) — иначе 422 с явной ошибкой; молчаливые подмены
     запрещены (наследие §4.3).
  2. Override никогда не заполняется моделью: мастер-билдер (`BuildSandboxDraft`)
     не имеет такого поля в контракте черновика; сервер игнорирует/отвергает
     попытку его протащить через модельный путь.
  3. Любая правка рецепта (в т.ч. текста override) сбрасывает закреплённый
     `image` профиля (как сегодня при смене base/packages в
     `UpdateSandboxProfile`).
  4. Встроенные профили (`builtin`) override не принимают никогда (каталог
     едет с обновлениями ядра).
  5. Пиннинг результата неизменен: digest в строку профиля, запуск `--pull=never`.
- **D3. Валидация текста override** (kernel/sandbox — строгая авторитетная
  сторона, workspace зеркалит для ранних ошибок):
  - непустой после trim, ≤ 16 KiB, UTF-8 без NUL;
  - минимум одна инструкция `FROM` (регистронезависимо); multi-stage разрешён;
  - запрещены: `ADD` (вреден и бесполезен без контекста), `COPY` без `--from`
    (нерабочий без контекста — ошибка с объяснением), `ONBUILD`;
  - каждая запрещённая конструкция даёт ошибку с номером строки и причиной.
- **D4. Действенные ошибки сборки.** `BuildDefinition` при отказе `apk`/`apt`
  выделяет виновный пакет (`ERROR: unable to select packages: … (no such
  package)` / `E: Unable to locate package …`) и отдаёт ошибку вида
  «пакет "sqlmap" не найден в репозиториях apk базы X; проверьте имя
  (подсказка apt↔apk-алиас при наличии в маппинге)» поверх сырого лога.
- **D5. Мастер перестаёт выдумывать пакеты.** Промпт `sandboxDraftPrompt`
  ужесточается: предлагать только пакеты, уверенно существующие в стандартных
  репозиториях базы; неуверенные — опускать; имена security/pentest-утилит
  (sqlmap, nikto, nmap и т.п.) предлагать только при полной уверенности
  наличия пакета в индексе базы. Черновик мастера по-прежнему заполняет форму,
  оператор редактирует и сохраняет.
- **D6. UX.** В форме профиля (Sandbox.tsx) появляется режимный переключатель
  «Собирать из базы / Свой Dockerfile». В режиме «Свой» текстовая область
  предзаполняется текущим композированным Dockerfile (как сегодняшний preview)
  и сохраняется как `dockerfile_override`; поля base/packages в этом режиме
  скрыты. Ошибки валидации PUT показываются оператору с номером строки.
- **D7. Ужесточение валидации по результатам design-ревью безопасности
  (T3, 2026-10-21; находки F-02…F-06).** В тексте override дополнительно
  запрещаются (ошибка с номером строки):
  1. parser-директивы `# syntax=` и `# escape=` (смена фронтенда сборки =
     сетевой pull произвольного frontend-образа на хосте); запрет устойчив к
     BOM/`\r\n`/лидирующим пробелам и покрывает любые директивы-формы
     `# key=` до первой инструкции (аудит F-01);
  2. `RUN … --network=host` (код в network namespace хоста при сборке),
     а также `--security=insecure`/`--security=privileged` и `--mount` вне
     `type=cache` (аудит F-02/F-03/F-04); флаг-секция разбирается после
     нормализации line-continuation по семантике docker (backslash+перенос
     удаляется без вставки пробела — иначе токен рвётся и уходит от проверки);
  3. верификация собранного образа (`verifyPinned`) переопределяет entrypoint
     (`--entrypoint true`) и запускает проверку под полным контуром изоляции
     песочницы (`--network=none`, read-only, `--cap-drop=ALL`,
     `no-new-privileges`, pids-limit, непривилегированный user — зеркало
     runtime-флагов kernel/sandbox/docker.go): исполняемый `true` из PATH
     образа (F-05) редуцируется к классу доверия обычного запуска песочницы.
  Осознанно принято (класс доверия D1/I-3): произвольные `FROM` и
  `COPY --from=<образ>` оставлены оператору — pull образов через daemon
  эквивалентен уже существующему пути внешних образов. DoS ресурсов демона
  при сборке — тот же класс, что у любой роли writer с docker-сокетом;
  компенсирующие контуры (gate-роли, аудит) не меняются.
- **D8. Санитизация вывода docker (закрытие F-06).** Вывод `docker build`
  (а также `pull`, верификационного `run` и пробы `version`) — недоверенный
  pull-класс: mutable/внешний `FROM` может вывести в лог что угодно. Ровно
  **один раз сразу после захвата вывода** применяется `sanitizeDockerOutput`
  (`kernel/sandbox/build.go`); классификация D4 (regex имени пакета) и
  форматирование ошибки работают с уже санитизированным текстом —
  поведение классификации не меняется. Что режется:
  - ANSI/VT-эскейп-последовательности: CSI (`ESC [ …`), строковые
    OSC/DCS/SOS/PM/APC (`ESC ] P X ^ _ …` до BEL или ST), иные ESC-формы;
  - C0-контрольные байты, кроме `\n` и `\t`; DEL (U+007F); C1 (U+0080–U+009F);
  - `\r\n` → `\n`, одиночный `\r` → `\n` (защита от перезаписи строк
    server-лога);
  - невалидный UTF-8 — байты вырезаются (результат всегда валидный UTF-8);
  - лимит **16384 байта**: остаётся хвост лога (итог ошибки сборки — в
    конце), в начале — маркер обрезки; срез по границе руны.
  Точки применения (`kernel/sandbox/build.go`): `BuildDefinition` (общий
  путь ошибки и путь классификации D4), `PullImage`, `verifyPinned`,
  `PreflightSocket`/`socketError`. Вне применения D8 (зафиксировано при
  закрытии F-06): `docker.go` несёт только сообщения демона/CLI без
  pull-контента (имя сети — константа, имя контейнера — сгенерированный
  hex), а `pinnedRef` встраивает вывод через `%q` (управляющие символы
  экранируются форматтером).

## 4. Контракт данных и API

- `workspace.SandboxProfile`: поле `DockerfileOverride string`
  `json:"dockerfile_override,omitempty"`; миграция
  `migrations/workspace/0002_*` добавляет колонку
  `dockerfile_override TEXT NOT NULL DEFAULT ''`.
- `ValidateSandboxProfile`: правила D2.1/D2.4 + зеркало D3.
- `kernel/sandbox`: новая `OverrideDefinition(profileID, dockerfile)` по образцу
  `CustomDefinition` (тег `temporality-sandbox-<id>:latest`, текст verbatim);
  `SetCustomProfileImage` принимает профили с override; маппинг ошибок D4.
- HTTP: `PUT/POST /v1/workspace/sandbox-profiles*` принимают поле;
  `POST …/preview` принимает опциональный `dockerfile_override` и возвращает
  либо валидированный текст, либо 422 с ошибкой построчно; `POST …/build`
  использует override verbatim. Аудит и события при правке рецепта — как для
  `sandbox.profile.updated` / `sandbox.profile.built` (существующие коды).
- UI/локали: `debugger/src/Sandbox.tsx`, `debugger/src/locales/{ru,en}.ts`.

## 5. Критерии готовности (приёмка)

- AC-1: профиль с `dockerfile_override` собирается через `POST …/build`,
  образ пинится digest-ом, `run_command` под ним работает (unit-тесты пути
  сборки + маппинга ошибок).
- AC-2: попытка сохранить профиль с override вместе с `base`/`packages` или с
  `image` → 422 с явной ошибкой (unit-тесты валидации).
- AC-3: builtin-профиль с override → отклоняется.
- AC-4: правка override сбрасывает `image` профиля (unit-тест store).
- AC-5: валидатор D3 отклоняет `ADD`, `COPY` без `--from`, `ONBUILD`, текст без
  `FROM`, переполнение размера — каждая ошибка называет строку (unit-тесты).
- AC-6: лог отказа `apk` с `sqlmap (no such package)` преобразуется в ошибку,
  называющую пакет `sqlmap` и подсказку (unit-тест маппинга).
- AC-7: мастер (промпт) не предлагает override и содержит ограничение по
  пакетам; контракт `SandboxDraft` не содержит поля рецепта (unit-тесты/ревью
  промпта).
- AC-8: UI: переключатель режимов, textarea предзаполняется композированным
  рецептом, сохранение передаёт `dockerfile_override`, ошибки валидации видны
  (vitest-тесты логики + зелёный `npm run build`).
- AC-9: `go test ./...`, `go vet ./...` — зелёные; debugger: vitest и
  `npm run build` — зелёные; регрессий в смежных тестах нет.
- AC-10: документация обновлена (`docs/sandbox-profiles.md`, при необходимости
  user-docs ru/en); принцип §4 уточнён по D1.
- AC-11 (гейт безопасности): заключение Security Auditor по I-3 получено;
  критические находки устранены либо явно признаны с обоснованием.

## 6. Вне объёма (зафиксировано, не делается)

- Предпроверка существования пакетов по онлайн-индексу apk/apt (зависит от
  сети в ядре) — возможное развитие, закрывающее RC-1 полностью.
- Изменение контура изоляции песочницы, модели профилей в целом, wizard-UX
  вне формы профиля.
