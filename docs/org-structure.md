# Оргструктура и модель доступа Temporality

## 1. Цель

Введение единой модели организационной иерархии, на которой строятся видимость и доступность всех сущностей Temporality: агентов, навыков, MCP-серверов, провайдеров и проектов.

Ключевое требование: ресурсы и настройки наследуются **сверху вниз** по дереву оргструктуры, а проекты могут охватывать несколько узлов и даже несколько компаний.

## 2. Проблематика текущей модели

Сейчас в системе сосуществуют три несвязанных механизма разграничения:

* глобальные списки (агенты, навыки, MCP-серверы) — всё видно всем;
* `workspace_user.projects` — список проектов в JSONB-колонке пользователя;
* `workspace_project.allowed_users` — список пользователей в JSONB-колонке проекта.

Этого достаточно для одного человека или маленькой команды, но модель не масштабируется:

* нет группировки по подразделениям и компаниям;
* нет наследования настроек сверху вниз;
* кросс-функциональные ресурсы (например, «навыки департамента разработки») выразить нельзя;
* права размазаны по разным сущностям и противоречат друг другу.

## 3. Целевая модель

### 3.1. Дерево оргструктуры

Один корневой узел на инсталляцию, глубина до 7–8 уровней в больших компаниях:

```text
Организация (Компания A)
├── Департамент разработки
│   ├── Отдел платформы
│   │   ├── Команда Temporality
│   │   └── Команда инфраструктуры
│   └── Отдел продукта
└── Департамент качества
Организация (Компания B)
└── ...
```

Узел оргструктуры (org unit):

```text
id            TEXT PRIMARY KEY
parent_id     TEXT NULL REFERENCES org_unit(id)     -- NULL только у корня
kind          TEXT   -- organization | department | team | ...
name          TEXT
path          TEXT   -- материализованный путь предков, напр. "a.b.c.d",
                     -- для быстрых запросов «узел + все предки»
created_at / updated_at
```

Материализованный путь (`path`) выбирается вместо ltree: достаточная производительность на глубине 7–8 и заметно проще в обслуживании, чем расширение Postgres. Путь пересчитывается триггером при перемещении узла (перемещение поддерева — редкая операция).

### 3.2. Привязка ресурсов

Каждый распределяемый ресурс получает nullable `org_unit_id`:

```text
workspace_agent.org_unit_id      TEXT NULL REFERENCES org_unit(id)
workspace_skill.org_unit_id      TEXT NULL
workspace_mcp_server.org_unit_id TEXT NULL
workspace_provider.org_unit_id   TEXT NULL
org_unit_trigger                 -- триггеры, привязанные к узлу
```

Семантика:

* `NULL` — доступно всей инсталляции (как сегодня);
* значение — доступно узлу и всему его поддереву.

Эффективная видимость ресурса для узла `U`:

```text
resource.org_unit_id IS NULL
OR resource.org_unit_id IN (путь U, включая сам U)
```

По `path` это один запрос: `org_unit_id = ANY(string_to_array(U.path, '.') || U.id)`.

### 3.3. Пользователи

```text
workspace_user.org_unit_id  TEXT NULL REFERENCES org_unit(id)
```

Пользователь принадлежит ровно одному узлу (вместо `projects` JSONB). Эффективные права вычисляются от его узла вверх по предкам. Администратор инсталляции остаётся флагом/ролью вне дерева.

### 3.4. Проекты

Проекты — не узлы дерева, а сущности, привязываемые к нескольким узлам many-to-many:

```text
workspace_project_org_unit
    project_id  TEXT REFERENCES workspace_project(id) ON DELETE CASCADE
    org_unit_id TEXT REFERENCES org_unit(id)      ON DELETE CASCADE
    PRIMARY KEY (project_id, org_unit_id)
```

Проект виден пользователю, если пересекаются:

* множество узлов проекта (включая их поддеревья), и
* узел пользователя с предками.

Это покрывает сценарии «проект двух компаний», «проект двух смежных департаментов» и текущий простой случай «проект одного узла».

### 3.5. Роли

Существующие роли (admin / operator / writer / reader) сохраняются и действуют в пределах видимости:

* роль на инсталляции — действует везде;
* роль на узле — действует в поддереве узла;
* внутри проекта — как сейчас.

## 4. Миграция с текущей модели

Миграция должна быть постепенной, без единого «большого взрыва»:

1. Создаётся корневой узел (одна организация).
2. Каждый существующий `workspace_user.org_unit_id = NULL` — все видят всё, поведение не меняется.
3. `workspace_user.projects` и `workspace_project.allowed_users` не удаляются сразу: чтение переключается на новую модель, старые колонки замораживаются и удаляются отдельной миграцией после проверки.
4. `NULL org_unit_id` у ресурсов сохраняет сегодняшнюю семантику «глобально» — ни одна существующая привязка не ломается.

## 5. API

* `GET/POST/PUT/DELETE /v1/org/units` — CRUD дерева (писать может только admin).
* `GET /v1/org/units/{id}/resources` — ресурсы, привязанные к узлу.
* `PUT /v1/org/resources/{kind}/{id}/binding` — привязка ресурса к узлу.
* Существующие списки (`GET /v1/workspace/skills` и т.д.) начинают фильтроваться по эффективной видимости вызывающего пользователя. Для admin-токенов ядра — без фильтра, чтобы рантайм не зависел от прав конкретного пользователя.

## 6. UI

* Раздел «Организация»: дерево узлов, drag-n-drop перемещения (аккуратно: с подтверждением, так как меняет видимость), инспекция узла — список ресурсов, пользователей, проектов.
* В формах редактирования агентов, навыков, MCP-серверов, провайдеров — поле «Доступность» с выбором узла (по умолчанию «Вся организация»).
* В форме проекта — мультивыбор узлов.
* В форме пользователя — выбор узла вместо списка проектов.

## 7. Фазы реализации и оценка

### Фаза 1 — модель данных и API дерева

Миграции, `org_unit` + `path`-триггер, CRUD API, привязка `org_unit_id` к ресурсам, сквозные Go-тесты эффективной видимости.

### Фаза 2 — авторизация по дереву

Фильтрация списков по эффективной видимости, роли на узлах, обновление gate в kernel и journal, тесты на пересечения прав (узел/поддерево/кросс-проект).

### Фаза 3 — UI организации

Дерево с инспекцией узла, поля доступности во всех формах ресурсов, мультивыбор узлов у проектов, выбор узла у пользователя, локализация.

### Фаза 4 — миграция и очистка

Мастер первоначальной настройки структуры, вычищение `allowed_users` / `user.projects`, документация.

## 8. Открытые вопросы

* Нужен ли аудит назначений (кто выдал доступ) — предложить в фазе 2 минимальный журнал изменений привязок.
* Приглашение внешних подрядчиков в узел чужой компании — сейчас предполагаем, что внешний участник добавляется узлом-«песочницей» в дереве компании-владельца.
* Импорт оргструктуры из внешних систем (HR/SCIM) — вне скоупа, зафиксировано как будущая работа.
