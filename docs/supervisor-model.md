# Модель-супервайзер: роль, кейсы и метрики человеческого фактора

Статус: принято (фаза 1 реализована). Связанные документы:
`agent-quality-loop.md`, `system-dashboard.md`, `human-knowledge-explorer.md`.

## 1. Роль

**Супервайзер** — installation-wide модель, которая работает **для
администратора**, а не над задачами пользователей. Она не выполняет работу
пользователей и не пишет в их артефакты; её продукция — суждения: оценки,
диагнозы, предложения, предупреждения. Каждое суждение имеет доказательную
базу (id ранов и событий) и остаётся предложением, пока человек не примет.

Сегодня супервайзер (= судья) уже: оценивает скиллы и изменения агентов
(golden-кейсы + калибровка согласия), упорядочивает области знаний. Настройка
— Агенты → «Настройки качества» (`/v1/workspace/supervisor`).

## 2. Настройки (фаза 1, реализовано)

| Параметр | Ключ | Назначение |
|---|---|---|
| Модель-супервайзер | `eval.judge.model` | роль судьи: оценки качества, упорядочивание областей знаний |

## 3. Каталог кейсов супервайзера (дорожная карта)

### Волна A — мониторинг проблем (наблюдатель)
- **A1. Триаж упавших ранов (реализовано).** После `run.failed` супервайзер читает трассу и
  пишет структурный диагноз: класс причины (ошибка модели / лимит песочницы /
  дефект харнеса / промпт агента / ошибка пользователя), доказательства,
  предложение. Пополняет очередь проблем администратора.
- **A2. Кластеризация повторяющихся сбоев инструментов.** Однотипные отказы
  (лимиты tmpfs, диапазоны CPU, таймауты провайдера) сворачиваются в один
  тикет «харнес сломан вот здесь» вместо россыми событий.
- **A3. Аномалии дашборда.** Рост p95, шторм ретраев, всплеск
  `secret.denied`, попытки выхода из песочницы — краткое пояснение
  естественным языком рядом с метрикой.

### Волна B — качество и развитие (помощник развития)
- **B1. Триаж противоречий знаний.** К паре «оспорено/утверждает иное» —
  черновик решения (какое знание устарело и почему), человек утверждает.
- **B2. Контрактные предложения.** По истории ранов агента: «проверки
  завершения не ловят X», «ограничение Y конфликтует с частой задачей Z» —
  через существующий `agent_propose`.
- **B3. Наблюдение за развитием.** Сравнение версий определения агента с
  исходами оценок — уже частично в контуре качества; супервайзер добавляет
  нарратив «что улучшилось/что деградировало».
- **B4. Гигиена знаний.** Расписание ревизии устаревших знаний
  (`at_risk`) с предложениями: подтвердить, обновить, списать.

### Волна C — пользовательские ошибки и трение
- **C1. Ошибки пользователей.** Паттерны: один и тот же вопрос повторно,
  отмены подтверждений, поправки, которые следовало быть новыми задачами,
  неотвеченные вопросы. Сводка для админа: «пользователи спотыкаются о X».
- **C2. Проверка intake-классификации.** Выборочный контроль: совпадает ли
  класс (поправка/новая задача) с фактическим исходом.
- **C3. Валидация цели поправки.** Перед стартом поправки супервайзер
  сверяет выбранную интейком цель («похоже, пользователь имел в виду ран N»)
  с описанием поправки — ловит неверный `amend_run_id` до запуска.
- **C4. Майнинг кандидатов в навыки.** Повторяющиеся последовательности тулов
  в успешных ранах — кандидаты на новый навык с готовым черновиком описания.
- **C5. Прогноз конфликтов знаний.** Новое знание семантически близко к
  существующему, но формулировки расходятся — предупреждение до записи, а не
  после (потребует семантический слой, §6).

Все кейсы работают на одной и той же поверхности: журнальные события →
структурное суждение супервайзера → очередь администратора. Ни одно суждение
не исполняется автоматически.

## 4. Vision-роутинг (фаза 1, реализовано)

Вызов модели, несущий изображения, направляется на модель из
`supervisor.vision.model`, если задана и отличается от модели запроса;

## 5. Человеческий фактор: HAB, HWT и Flow Efficiency (фаза 1, реализовано)

Метрики разделяют два разных явления, которые раньше смешивались в
«human approval budget»:

| Метрика | Канбанский аналог | Определение |
|---|---|---|
| **HAB — Human Attention Spend** («внимание») | touch time | Оценка времени внимания: чтение итоговых и промежуточных заключений, принятие подтверждений, обдумывание и написание ответов |
| **HWT — Human Wait Time** («простой») | queue wait time | wall-clock время, которое работа простояла в ожидании человека (вопрос поднят → решён), вне зависимости от того, сколько внимания это заняло |
| **Flow Efficiency** | flow efficiency | `HAB / (HAB + HWT)` — доля человеческой шкалы времени, которая ушла на реальное внимание, а не на простой |

### Как считается HAB (оценка, коэффициенты настраиваются)

- решение по подтверждению/сверке: `supervisor.hab.approval_seconds` (45с);
- ответ на `ask_human`: база `answer_base_seconds` (20с) + набор текста
  (длина ответа / 5 символов на слово / `reading_wpm`);
- чтение сгенерированных заключений: все `model.completed` окна,
  output-токены × 0.75 слов/токен ÷ `reading_wpm`.

### Как считается HWT

Σ (момент решения − момент постановки вопроса) по разрешённым
подтверждениям/вопросам в окне. Это чистая задержка потока — канбан-очередь.

### Где смотреть

Дашборд → обзор → карточка «Человеческий фактор»: HAB, HWT, Flow Efficiency
и счётчики решений/ответов за окно. Появление HWT ≫ HAB — сигнал: вопросы
зависают, поток блокируется на людях.

## 6. Семантический слой знаний (фаза 2, реализовано)

Модель эмбеддингов — **локальная и фиксированная**, работает **в процессе
ядра** через pure-Go движок rembed (`intfloat/multilingual-e5-small`,
384-мерные векторы, 100+ языков, weight-only int8): ни отдельного сервиса,
ни провайдеров, ни ключей. Провайдерские эмбеддинги выпилены: облачные
каталоги не отдают эмбеддинг-модели, а качество локального e5 для наших
коротких пропозиций выше (multilingual-e5 специально обучен на 100+ языках).
Модель лениво загружается с HF Hub при старте ядра в персистентный кэш
(`/var/cache/rembed`, volume `rembed_cache`); до готовности подсказки
работают в лексическом режиме.

Матчер подсказок сегодня лексический (тиры: точные попадания тем/сущностей →
IDF-термины). Семантический слой добавит тир «по смыслу» на эмбеддингах —
найденное будет помечаться `semantic:<score>` в `matched_by`.

### Что нужно

1. **Движок инференса** — pure-Go библиотека rembed в процессе ядра
   (`KERNEL_EMBEDDINGS_MODEL`, по умолчанию e5-small; `KERNEL_EMBEDDING_WORKERS`
   ограничивает CPU), без HTTP-хопа и внешних зависимостей.
2. **Хранение** — журнал-БД уже на pgvector: миграция добавляет к знанию
   вектор (размерность — под выбранную модель) и штамп версии модели
   эмбеддингов. Смена модели ⇒ фоновый пересчёт.
3. **Наполнение** — ingest-хук на `knowledge.proposed/corrected` + фоновый
   проход по записям без вектора/с чужим штампом.
4. **Запрос** — слот подсказки эмбеддит текст задачи; косинусная близость
   даёт новый тир в `hintCandidate` (между точными сущностями и IDF-лексикой),
   существующие механизмы (понижение за novelty B5, бюджеты, исходы) — без изменений.
   e5-префиксы: kernel добавляет `query: ` к тексту слота и `passage: ` к
   пропозициям знаний (rembed отдаёт текст как есть — без префиксов e5
   молча теряет качество).
5. **Деградация** — модель не настроена/недоступна ⇒ ровно текущее
   лексическое поведение + счётчик пропусков в health.
6. **Оценка эффекта** — A/B по существующим исходам подсказок
   (helpful/harmful) до/после включения; золотые запросы в оценку.

Оценка объёма: миграция + клиент провайдера + ingest-хук + тир в матчере +
бейдж в UI — один сосредоточенный релиз.
