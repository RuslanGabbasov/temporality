# Профили песочниц (Sandbox Profiles) [L1-360]

## 1. Цель

Дать агентам разные среды исполнения команд: не один образ на всю
инсталляцию, а каталог профилей (Go, Node, Python, браузерные E2E),
которые администратор собирает и закрепляет, а владелец агента назначает
агенту по типу задачи.

## 2. Проблематика текущего состояния

- Поле `sandbox_profile` карточки агента (`restricted | standard |
  privileged`) мертво: оно сохраняется, показывается в UI и передаётся в
  компиляцию промпта, но ни разу не читается. Реальные ограничения
  контейнера одинаковы для всех агентов.
- Образ песочницы один на инсталляцию (`KERNEL_SANDBOX_IMAGE` или
  `workspace_setting.sandbox_image`): `golang:1.27-alpine` + git, ssh,
  curl, jq, bash, python3, ripgrep. QA-агенту нужен Node и Playwright —
  их в образе нет и без смены образа быть не может.
- Кэш-монтирование `/cache` зашито под Go (`GOCACHE`, `GOMODCACHE`):
  другим тулчейнам кэши не достаются.
- Ресурсы контейнера (память, CPU, размер tmpfs) — глобальные env-параметры
  раннера; браузерным сборкам нужно больше, а повышать всем нельзя.

## 3. Основные понятия

### 3.1. Профиль песочницы (Sandbox Profile)

Сущность workspace:

| Поле | Смысл |
|---|---|
| `id` | стабильный слаг (`node`, `browser-e2e`) |
| `name`, `description` | человекочитаемые название и назначение |
| `image` | digest-pinned ссылка на образ (`repo@sha256:…`); пусто, пока не собран |
| `toolchains` | теги тулчейнов (`go`, `node`, `python`, `browser`) — для UI и подсказок |
| `memory`, `cpus`, `scratch_size`, `tmp_size` | ресурсные переопределения; пусто = значения инсталляции |
| `cache_env` | `KEY=VALUE`-переменные кэшей, указывающие в `/cache` (`NPM_CONFIG_CACHE=/cache/npm`) |
| `builtin` | встроенный профиль каталога; нельзя удалить, можно пересобрать и подстроить ресурсы |

### 3.2. Резолвинг на старте рана

Цепочка: профиль агента → пусто = профиль инсталляции (образ раннера,
текущее поведение без изменений). Разрешение происходит при построении
`RunInput` (все пути запуска: задачи, триггеры, чат, делегирование через
run-config). Результат — `SandboxSpec` (образ + ресурсы + кэш-переменные),
который едет с раном до границы исполнения.

### 3.3. Граница исполнения

`run_command` собирает `sandbox.Request` из `SandboxSpec`: образ,
ресурсы и кэш-переменные применяются на каждый вызов команды. Профиль
не попадает в промпт и не виден модели как отдельная сущность — среда
исполнения это инфраструктура, а не знание агента.

## 4. Принципы

1. **Безопасность не зависит от профиля.** Изоляция одна для всех:
   read-only rootfs, `--cap-drop=ALL`, `no-new-privileges`, pids-limit,
   noexec `/tmp`, uid 10001. Профиль меняет только тулчейн и ресурсы.
2. **Только digest.** Любой образ — встроенной сборки или внешний —
   закреплён полным `@sha256:…` и запускается с `--pull=never`
   (docs/sandbox-security-matrix.md). Тег без digest не принимается.
3. **Молчаливый фолбэк запрещён.** Если агенту назначен профиль, чей
   образ не собран/отсутствует, команда падает с явной ошибкой
   «профиль не собран», а не выполняется в чужом окружении: тихая
   подмена тулчейна хуже видимого сбоя.
4. **Профиль — не привилегия.** «Привилегированных» профилей нет:
   мёртвая тройка `restricted/standard/privileged` исчезает. Уровни
   доступа остаются там, где они реально работают: `network_access`,
   `read_only`, орг-политики, квоты бюджета.
5. **Сборка — административное действие.** Пересборка образа профиля
   меняет то, что могут исполнять команды агентов, поэтому попадает
   в аудит и журнал событий.

## 5. Каталог встроенных профилей

| id | Основа | Тулчейны | Особенности |
|---|---|---|---|
| `node` | `node:22-alpine` + git, curl, jq, bash, ripgrep | node | `NPM_CONFIG_CACHE=/cache/npm` |
| `python` | `python:3.12-alpine` + git, curl, jq, bash, ripgrep | python | `PIP_CACHE_DIR=/cache/pip`, `UV_CACHE_DIR=/cache/uv` |
| `browser-e2e` | `mcr.microsoft.com/playwright:v1.49.0-jammy` | node, browser | память 2g, scratch 1g, `/cache/ms-playwright` под браузеры |

Профиль по умолчанию (пустое значение) — текущий образ инсталляции;
отдельной строки каталога для него нет, UI показывает его как
«По умолчанию». Dockerfile-ы встроенных профилей живут в коде ядра
(`kernel/sandbox`), как и базовый `EmbeddedDockerfile`.

## 6. API

| Метод | Путь | Доступ | Смысл |
|---|---|---|---|
| GET | `/v1/workspace/sandbox-profiles` | reader | каталог с флагом `available` (образ есть в локальном Docker) |
| POST | `/v1/workspace/sandbox-profiles` | writer | создать кастомный профиль (внешний digest-pinned образ) |
| PUT | `/v1/workspace/sandbox-profiles/{id}` | writer | изменить кастомный; для встроенного — только ресурсы (memory, cpus, scratch, tmp, cache_env), идентичность каталога и image не трогаются |
| DELETE | `/v1/workspace/sandbox-profiles/{id}` | writer | удалить кастомный (встроенный — 409) |
| POST | `/v1/workspace/sandbox-profiles/{id}/build` | writer | собрать образ встроенного профиля и закрепить digest |

События журнала: `sandbox.profile.built`, `sandbox.profile.created`,
`sandbox.profile.updated`, `sandbox.profile.deleted`; те же действия
пишутся в аудит. Назначение профиля агенту — обычное изменение карточки
агента.

## 7. Наблюдаемость

- `exec_context` рана несёт `sandbox_profile` — видно, в какой среде
  работал ран.
- События `run_command` не меняются: образ детерминирован профилем из
  `exec_context`, дублировать его в каждой команде не нужно.

## 8. UI

- **Настройки → Песочницы**: каталог профилей (название, тулчейны,
  digest, ресурсы, статус «собран/не собран»), кнопка «Собрать» для
  встроенных, создание/удаление кастомных; правка ресурсов — и для
  встроенных (memory, cpus, scratch, tmp, cache_env), и для кастомных.
  Пересборка встроенного профиля сохраняет настроенные ресурсы.
- **Карточка агента**: вместо мёртвого селекта — выбор профиля из
  каталога со статусом сборки; «По умолчанию» = образ инсталляции.
- Визард создания агента больше не предлагает уровень песочницы:
  среда исполнения назначается профилем осознанно, а не генерируется.

## 9. Фазы реализации

### Фаза 1 — реестр и назначение (текущая)
- Сущность `workspace_sandbox_profile`, миграция 000070; мёртвые значения
  `restricted/standard/privileged` в карточках агентов мигрируются в пустое.
- Каталог встроенных профилей (node, python, browser-e2e) с сидингом.
- `SandboxSpec` в `RunInput`/`ToolRequest`; образ, ресурсы и кэш-переменные
  в `sandbox.Request`.
- Резолвинг профиля на старте рана, `sandbox_profile` в `exec_context`.
- API каталога + сборка + аудит/события; валидация при сохранении агента.
- UI: страница «Песочницы», селект профиля в карточке агента.

### Фаза 2 — управление образами
- Конструктор образов из компонентов (по мотивам devcontainer features):
  базовый профиль + слои тулчейнов без ручного написания Dockerfile.
- Внешние реестры образов (pull через digest, pinning), сканирование
  образов перед закреплением.
- Версии образов профиля: digest в карточке профиля + история сборок.

### Фаза 3 — политики
- Org-политики разрешённых профилей по структурным единицам.
- Альтернативные рантаймы изоляции (gVisor) как опция профиля — только
  при реальной мультиарендной нагрузке.

## 10. Критерии готовности (фаза 1)

- Агенту назначен `browser-e2e`, образ собран → `run_command node -v`
  отвечает версией Node; `/cache/npm` сохраняется между командами.
- Профиль назначен, образ не собран → `run_command` возвращает явную
  ошибку про несобранный профиль; ран не стартует в чужом образе.
- `restricted/standard/privileged` нигде не принимаются: сохранение
  агента с таким значением — 422.
- Все образы в `sandbox.Request` — только `@sha256:…`; тест на
  отказ от тега.
- `exec_context` рана с профилем содержит `sandbox_profile`.
- Сборка профиля доступна только writer; пишет аудит и событие журнала.
- `go test ./... -count=1` зелёный; UI собирается, локализация ru/en.

## 11. Открытые вопросы

- Проектный профиль по умолчанию (проект → свой базовый образ) — нужен
  ли, если у команды один основной тулчейн? Решение отложить до запросов.
- Автосборка недостающего профиля при назначении (долгий docker build в
  момент сохранения карточки агента) — пока намеренно нет.
- Предустановка тулчейнов нескольких типов в одном образе (Nix/devbox)
  как альтернатива каталогу — оценить в фазе 2 по реальным болям.

## 12. Архитектурные ограничения

- Рантайм остаётся Docker: замена на microVM (Firecracker, Kata) не
  рассматривается до мультиарендных инсталляций.
- Значения кэш-переменных указывают только в `/cache` — персистентный
  пер-проектный кэш вне git-workspace; значения вне `/cache` отвергаются.
- Digest-закрепление обязательно для всех профилей, включая кастомные.
