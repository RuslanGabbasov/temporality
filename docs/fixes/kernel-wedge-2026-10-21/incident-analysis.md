## Установленные факты (подтверждено доказательствами)

- **F1.** Ядро не было «мёртвым» на протяжении инцидента: периодические циклы (storage.snapshot 14:29:10, 14:59:38) и запись в БД через API (reconcile 15:04–15:05, updateTask 15:14:35) работали. «Жёсткое падение» — восприятие; фактически это **частичный завис + серия перезапусков процесса** (см. F2).
- **F2.** Процесс ядра перезапускался многократно: буты 10:52:38, 10:53:36 (≈1 мин друг от друга — похоже на crash-loop), 14:15:54, 14:29:10, 14:59:38. Это либо падения процесса с авто-рестартом (`restart: unless-stopped`), либо ручные рестарты — различить невозможно: логи уничтожены `docker compose down` (см. F7).
- **F3.** Отправка сообщений в чат упиралась именно в `POST /v1/workspace/tasks/{taskID}/runs`: `createTask`/`updateTask` на том же API проходили за секунды до/после, а старт рана не создавал ни строки в `workspace_run`, ни ответа до браузера («NetworkError…» = fetch отклонён без HTTP-ответа; стандартная ошибка Firefox `TypeError`).
- **F4.** Три активных прогона зависли «внутри» вызова модели: последнее событие каждого — `model.started` (14:09:15, 14:13:38, 14:28:55), дальше — тишина. Никаких `model.attempt` / `model.failed` по ним нет — то есть даже штатная лестница ретраев не сработала (в здоровом прогоне 15:27–16:17 та же система исправно пишет `model.attempt` → `activity_retry`).
- **F5.** «Пропадает список проектов» объясняется кодом UI: `loadProjects` (Layout.tsx) при любой ошибке молча `catch { /* ignore */ }` и возвращает `[]` — при перезагрузке страницы во время недоступности API селектор проектов пустеет. Пользователь перезагружал страницу многократно — доказано 4 дублями задачи «создай PR»: `taskId` живёт только в памяти React и не сохраняется в серверный транскрипт чата, поэтому после каждой перезагрузки следующее сообщение создаёт новую задачу.
- **F6.** Восстановление только полным пересозданием стека — согласуется с зависшим состоянием процесса/соединений, которое не лечится само.
- **F7.** Провайдер модели (`token-plan-sgp.xiaomimimo.com`) сегодня нестабилен: `model.attempt` фиксируют `PROTOCOL_ERROR; received from peer`, `unexpected EOF`, `stream read (idle timeout…)`. Это внешний триггер.
- **F8.** Окружение: `TEMPORALITY_MODEL_ACTIVITY_TIMEOUT=10m`, `TEMPORALITY_MODEL_MAX_OUTPUT_TOKENS=131072`, `TEMPORALITY_MODEL_TIMEOUT=180s`, стрим-вотчдоги 90s/2m/4m.

## Дефекты кода (статический анализ, подтверждено чтением исходников)

- **D1. Бездедлайновые Temporal-RPC из HTTP-хендлеров.** `POST /v1/workspace/tasks/{taskID}/runs` → `temporalClient.ExecuteWorkflow(r.Context(), …)`; `/nudge`, `/note` → `SignalWorkflow(r.Context(), …)` — таймаута нет ни у вызова, ни у `http.Server` (задан только `ReadHeaderTimeout: 5s`; нет `WriteTimeout`/`IdleTimeout`). Зависшее gRPC-соединение с Temporal вешает хендлер навсегда; браузер получает обрыв транспорта вместо ошибки.
- **D2. Тихие зависания вызова модели.** Раны зависших прогонов навсегда остаются в `started`: ни `model.failed`, ни `model.attempt` — см. F4. Требуется гарантированный «громкий» отказ: вотчдог на весь `CallModel` (не только на стрим) + журналирование исхода любой попытки.
- **D3. UI: безмолвная деградация.** `loadProjects` глотает ошибки → пустой список проектов без состояния ошибки и ретрая; `request()` (workspaceApi.ts) без таймаутов; `taskId` бесследно теряется при перезагрузке (F5).
- **D4. Недиагностируемость.** Логи ядра живут только в stdout контейнера и уничтожаются `docker compose down`; `pprof`/дампы горутин не подключены. Из-за этого точный механизм зависания (D1/D2/иной) постфактум **невозможно подтвердить**.

## Гипотезы (НЕ подтверждены)

- **H1.** Триггер инцидента — зависшие HTTP-вызовы к нестабильному провайдеру модели (F7), после которых процесс/воркер деградировал и перезапускался (F2). Сильная корреляция (все три зависших прогона остановились на `model.started`), но причинность не доказана.
- **H2.** Обрыв ответа `startRun` — следствие падения процесса посреди записи ответа либо недоступности nginx в момент рестарта контейнеров. Оба варианта дают `NetworkError`; выбрать между ними нельзя.
- **H3.** Латентный дедлок `embedMu` из спеки saga-embeddings (D3 там) НЕ является причиной: в текущем коде ветка недостижима (канал `ready` закрывается только при успехе) — проверено чтением `kernel/agent/embeddings.go`.

## Что невозможно подтвердить

- Точный механизм зависания/падения ядра в окне 14:02–15:16 — stderr ядра, error-лог nginx и события docker уничтожены пересозданием контейнеров (`docker compose down`). Это и есть главный урок: нужна персистентная диагностика (D4).
