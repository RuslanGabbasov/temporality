# Спецификация: устойчивость ядра к зависанию вызовов модели и недоступности Temporal

Дата: 2026-10-21. Инициатор: ruslan. Сага: saga-temporality-5636f9.
Основание: docs/fixes/kernel-wedge-2026-10-21/incident-analysis.md (F1–F8, D1–D4).

## Контекст

Инцидент 2026-10-21: отправка сообщений в чат падала на `POST /v1/workspace/tasks/{id}/runs`
(транспортный NetworkError без HTTP-ответа), список проектов в UI пустел, раны зависали
на `model.started` без ретраев, восстановление — только `docker compose down/up`.
Точный механизм зависания постфактум недоказуем (логи уничтожены) — поэтому вводится
персистентная диагностика, чтобы следующий инцидент был диагностируем.

## Объём

- `cmd/agent-kernel/main.go` — только точки вызовов Temporal-RPC в HTTP-хендлерах
  (POST /v1/workspace/tasks/{taskID}/runs, /nudge, /note, GET /v1/agent/runs,
  resolveRunState) и конфигурация `http.Server`. Правки строго аддитивные:
  в рабочем дереве висит чужой WIP, его ханки не трогать.
- `debugger/src/Layout.tsx` — состояние ошибки загрузки проектов (файл не в WIP).
- `debugger/src/workspaceApi.ts` — таймаут `request()` (аддитивно; файл в WIP — не менять
  существующие ханки).
- ВНЕ ОБЪЁМА (зафиксировано как follow-up): полный аудит вотчдогов `CallModel` (D2),
  персистентные логи ядра, pprof/дампы горутин (D4), персистентный `taskId` чата (D3,
  часть про дубли задач).

## Требования

- **R1 (дедлайн Temporal-RPC)**: каждый Temporal-RPC, инициируемый из HTTP-хендлера
  (ExecuteWorkflow, SignalWorkflow, DescribeWorkflowExecution, GetWorkflow-получение
  результата), ограничен контекстом с таймаутом (дефолт 15 с, override
  `KERNEL_TEMPORAL_RPC_TIMEOUT`). По истечении — HTTP 503 с внятной ошибкой
  (`temporal rpc timeout: …`), никаких вечных зависших запросов.
- **R2 (HTTP-сервер)**: у `http.Server` выставлены `WriteTimeout` и `IdleTimeout`
  (дефолт 120 с / 120 с, override env), чтобы зависший хендлер не держал соединение вечно.
- **R3 (UI: видимость ошибки)**: селектор проектов при ошибке загрузки показывает
  состояние ошибки с кнопкой «Повторить», а не молча пустой список; `request()` получает
  общий таймаут (дефолт 60 с) с типичной ошибкой `ApiError`/`timeout`, без изменения
  контракта ответов.
- **R4 (тесты)**: юнит-тесты на R1 (фейковый Temporal-клиент: медленный RPC → 503 в
  пределах дедлайна; быстрый → штатный ответ) и на R3 (loadProjects: ошибка →
  состояние ошибки + ретрай восстанавливает список). Тесты UI — vitest (в репо уже есть).
- **R5 (совместимость)**: контракты API/JSON не меняются; поведение при здоровом
  Temporal не меняется (таймаут заведомо больше нормальных RPC); чужой WIP в рабочем
  дереве не откатывается и не редактируется.

## Критерии приёмки

1. `go build ./...`, `go vet ./...`, `go test ./cmd/agent-kernel/ ./kernel/agent/` — чисто.
2. `npm run build` (debugger) и `npx vitest run` — чисто, включая новые тесты R4.
3. Инъекционный тест доказывает: медленный Temporal-RPC прерывается дедлайном и
  хендлер возвращает 503, а не зависает.
4. Diff ограничен файлами объёма; незакоммиченный WIP не тронут.

## Валидация требований

- **Полнота**: требования покрывают подтверждённые дефекты D1 и D3; D2/D4 вынесены в
  follow-up явно (объём ограничен бюджетом итерации).
- **Логическая непротиворечивость**: R1–R5 не конфликтуют; R2 не влияет на SSE-стримы
  (WriteTimeout действует на хендлер целиком — стримы `/stream`, `/tokens` живут в
  отдельных хендлерах и должны использовать `Flush`-цикл с продлением; при конфликте
  стрим-хендлеры исключаются из WriteTimeout явно — фиксируется в коде комментарием).
- **Техническая реализуемость**: да — правки локальны, тесты достижимы фейками,
  сборка/тесты доступны в песочнице.
