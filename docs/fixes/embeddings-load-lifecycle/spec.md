# Спецификация: ремонт жизненного цикла загрузки embedding-модели в ядре

Дата: 2026-10-21. Инициатор: ruslan (запрос: «не костыли, а починим код, который это делает»).
Сага: saga-embeddings-7c1709.

## Контекст

Локальная установка (docker-compose из этого репозитория) показывает readiness-чек
`embeddings` с `detail: "load not attempted"` бесконечно. Замеры с хоста установки:
сеть из контейнера до HF/CDN работает (~2.3 МБ/с), `/var/cache/rembed` пуст и записываем,
`KERNEL_EMBEDDINGS_MODEL=intfloat/multilingual-e5-small`, токен-файлов нет. Попытка
загрузки падает быстро, но её причина невидима: код ядра теряет текст ошибки.

## Объём

Чинится код ядра (оркестрация загрузки): `kernel/agent/embeddings.go`,
`cmd/agent-kernel/embeddingsbackfill.go`, точечно `cmd/agent-kernel/main.go`.

ВНЕ объёма: внутренняя устойчивость внешней библиотеки `github.com/rostamlabs/rembed`
v0.3.1 (жёсткий URL HF, отсутствие докачки/ретраев, `cleanup()` при ошибке). Это
внешняя зависимость; возможный follow-up — форк/обёртка с докачкой. Зафиксировано явно.

## Подтверждённые дефекты (проверено чтением исходников, 2026-10-21)

- **D1** — `startEmbeddingPreloadLocked` (kernel/agent/embeddings.go): при ошибке
  `rembed.Load` сохраняет `embedState.err`, но делает `embedState.ready = nil` и не
  закрывает канал `ready` (закрывается только при успехе). Комментарий к
  `embedderState.ready` («closed on load success OR failure») противоречит коду.
  Следствие: ждущие в `getEmbedder` висят до `embedWaitTimeout` и получают ложную
  ошибку «embedding model is still loading — retry shortly».
- **D2** — `EmbeddingsStatus`: при `embedState.ready == nil` возвращает
  «load not attempted» даже когда попытка уже была и упала; `embedState.err`
  в эту ветку не попадает. readiness `detail` (cmd/agent-kernel/main.go:1835 —
  `"detail": embedStatus.Error`) поэтому никогда не показывает реальную причину.
- **D3** — `getEmbedder`: ветка `if embedState.err != nil` выполняет второй
  `embedMu.Lock()` при уже удерживаемом `embedMu` (Lock … defer Unlock, затем
  вложенный Lock) на нерекурсивном мьютексе → дедлок. Сейчас латентен (недостижим,
  пока D1 не закрывает канал при ошибке), но станет достижим после починки D1.
- **D4** — повтор загрузки происходит только из вызовов `EmbedTexts` → `getEmbedder`;
  бэкфилл-цикл зовёт их только когда есть знания без векторов
  (cmd/agent-kernel/embeddingsbackfill.go, `if len(gaps) == 0 { return }`), а
  `StartEmbeddingPreload()` вызывается один раз на буте (main.go:6962). Итог:
  пустая база + упавшая загрузка = «load not attempted» навсегда, никто не пробует снова.
- **D5** — исход загрузки (успех/ошибка, модель, кэш-каталог, длительность) не
  логируется ни ядром, ни rembed в библиотечном пути → инцидент 2026-10-21 07:47
  постфактум недиагностируем.

## Требования

- **R1 (видимость ошибки)**: текст ошибки `rembed.Load` сохраняется, логируется
  (уровень error; модель, кэш-каталог, текст ошибки) и отражается в
  `EmbeddingsStatus.Error`, а значит и в readiness `detail`. Состояние «попытка
  упала» не маскируется под «load not attempted».
- **R2 (корректная машина состояний)**: канал `ready` закрывается и при успехе, и при
  ошибке; ожидающие получают реальную ошибку немедленно, а не по таймауту. Ровно одна
  загрузка в полёте в каждый момент. Двойной лок устранён (D3). Ложный текст
  «embedding model is still loading» не возвращается, когда загрузка уже упала.
- **R3 (авто-повтор)**: неудачная попытка повторяется автоматически с ограниченным
  экспоненциальным бэкоффом (старт ~30 с, потолок ~5 мин), **независимо** от наличия
  знаний без векторов; без busy-loop и без параллельных дублей загрузки. Успешный
  вызов `EmbedTexts`/`StartEmbeddingPreload` также может инициировать повтор немедленно.
- **R4 (журнал/логи)**: успех загрузки логируется (модель, длительность); в логах ядра
  каждая упавшая попытка содержит реальную причину.
- **R5 (тесты)**: машина состояний покрыта юнит-тестами через инъекцию загрузчика
  (функция `rembed.Load` выносится в переменную/интерфейс для тестов): успех, ошибка
  (статус содержит текст ошибки, канал закрыт, ждущие получают ошибку), авто-повтор,
  отсутствие дедлока в ветке ошибки.
- **R6 (совместимость)**: JSON-контракт `EmbeddingsStatus` (`model`, `ready`, `error`)
  и ключи readiness-чека (`key`, `configured`, `used_by`, `fix`, `detail`) сохраняются;
  меняется только семантика `error`/`detail` (теперь несут реальную причину).
  Допустимо уточнить строку `fix` в main.go, если она остаётся фактически верной.

## Критерии приёмки

1. `go build ./...`, `go vet ./...` — чисто (из /workspace/temporality).
2. `go test ./kernel/agent/ ./cmd/agent-kernel/` — чисто, включая новые тесты R5;
   `go test -race ./kernel/agent/` — чисто.

> **Поправка к критерию 2 (2026-10-21, по результатам QA-прогона):** полный
> `go test -race ./kernel/agent/` падает **и на базе 223eb0a** — 7 пре-существующих
> тестов `kernel/agent/workflow_test.go` (гонки в самом тестовом коде: счётчики в
> activity-функциях без синхронизации, строки ~261, ~1193). Это дефект вне объёма
> (не embeddings), он не блокирует итерацию. Приёмка по race: `go test -race` чист
> для embeddings-тестов и в изменённом коде гонок нет; гонки `workflow_test.go`
> выносятся в отдельную задачу.
3. Инъекционный тест доказывает: после ошибки `EmbeddingsStatus.Error` содержит текст
   ошибки (не «load not attempted»), повтор запускается без внешних вызовов, ожидающие
   не зависают.
4. Diff затрагивает только файлы объёма; сопутствующие незакоммиченные изменения в
   рабочем дереве не откатываются и не переписываются.

## Валидация требований

- **Полнота**: исходный запрос («починить код, который это делает») конкретизирован до
  R1–R6 на основе подтверждённых дефектов D1–D5. Непокрытый остаток — устойчивость
  скачивания внутри rembed — вынесен за рамки явно (см. «Объём»).
- **Логическая непротиворечивость**: R1–R6 не конфликтуют; R2 устраняет латентный
  дедлок, который иначе активировала бы починка D1.
- **Техническая реализуемость**: да — изменения локальны, тесты достижимы через
  инъекцию загрузчика; сборка и тесты доступны в песочнице.
