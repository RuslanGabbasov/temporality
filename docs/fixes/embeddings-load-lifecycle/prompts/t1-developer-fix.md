## Цель

Устранить дефекты D1–D5 жизненного цикла загрузки embedding-модели (см. ниже) так,
чтобы ошибка загрузки была видна оператору, попытки повторялись автоматически, а
ожидающие не зависали. Полная спецификация: docs/fixes/embeddings-load-lifecycle/spec.md
(лежит в worktree).

## Входные данные (проверено лидом чтением исходников)

Файлы объёма: kernel/agent/embeddings.go (основной), cmd/agent-kernel/embeddingsbackfill.go,
точечно cmd/agent-kernel/main.go (строки примерно ~1812, ~1834-1835, ~6962 — ищите по
символам: readiness-чек `embeddings`, вызов `StartEmbeddingPreload`; номера могут отличаться).

- D1: в `startEmbeddingPreloadLocked` при ошибке `rembed.Load` код делает
  `embedState.ready = nil` и не закрывает канал `ready` (закрытие только при успехе);
  комментарий `embedderState.ready` («closed on load success OR failure») врёт. Ждущие
  в `getEmbedder` висят до `embedWaitTimeout` и получают ложную ошибку
  «embedding model is still loading — retry shortly».
- D2: `EmbeddingsStatus` при `embedState.ready == nil` возвращает «load not attempted»
  даже после упавшей попытки; `embedState.err` туда не выводится → readiness `detail`
  (`"detail": embedStatus.Error`) не показывает причину.
- D3: в `getEmbedder` ветка `if embedState.err != nil` делает второй `embedMu.Lock()`
  при уже удерживаемом мьютексе → дедлок (сейчас латентный, станет достижим после D1).
- D4: повтор загрузки идёт только из вызовов `EmbedTexts`; бэкфилл зовёт их только при
  наличии gap'ов (`if len(gaps) == 0 { return }` в embeddingsbackfill.go), а
  `StartEmbeddingPreload()` вызывается один раз на буте. Пустая база → загрузку больше
  никто не пробует.
- D5: исход загрузки не логируется вообще (rembed в библиотечном пути молчит).

## Требования (из спецификации, обязательно все)

- R1: текст ошибки `rembed.Load` сохраняется, логируется (error: модель, кэш-каталог,
  текст ошибки) и попадает в `EmbeddingsStatus.Error` и readiness `detail`. Состояние
  «попытка упала» не маскируется под «load not attempted».
- R2: канал `ready` закрывается и при успехе, и при ошибке; ожидающие получают реальную
  ошибку немедленно; ровно одна загрузка в полёте; двойной лок устранён.
- R3: неудачная попытка повторяется автоматически с экспоненциальным бэкоффом
  (~30 с → потолок ~5 мин), независимо от gap'ов; без busy-loop и параллельных загрузок;
  внешний вызов может инициировать немедленный повтор.
- R4: успех тоже логируется (модель, длительность).
- R5: юнит-тесты через инъекцию загрузчика (вынести `rembed.Load` в переменную
  `var loadEmbedder = rembed.Load` или аналог): успех; ошибка (статус содержит текст
  ошибки, канал закрыт, ждущие получают ошибку без 10-секундного ожидания); авто-повтор;
  отсутствие дедлока в ветке ошибки (включая `go test -race`).
- R6: JSON-контракт `EmbeddingsStatus` (model/ready/error) и ключи readiness-чека
  (key/configured/used_by/fix/detail) сохраняются; допустимо уточнить строку `fix`.
