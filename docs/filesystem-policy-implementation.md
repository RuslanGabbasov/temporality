# Filesystem Policy: заметки к реализации (ветка feat/filesystem-policy)

Сопроводительные заметки к ТЗ [`docs/filesystem-policy.md`](filesystem-policy.md):
решения, принятые при встраивании в существующую кодовую базу, влияние на
уже развёрнутые инсталляции и известные риски. Обновляется по мере этапов
(P0 → P1 → P2).

## 1. Семантика, зафиксированная в P0

- **`nil`/отсутствующее измерение = без ограничений** (§3.5). Ряд политики без
  `filesystem` не сужает ничего; поведение инсталляции без файловых правил
  байт-в-байт прежнее.
- **Пустой непустой список (`[]`) = ничего не разрешено** — та же развилка
  `nil` vs `[]`, что уже используется в `PolicyAllowsList`. Нормализация при
  записи: отправленный пустой список читается как `nil` («не задано»).
- **`deny` — абсолютный приоритет**, объединяется ОБЪЕДИНЕНИЕМ по уровням:
  запрет предка не отменяется дочерней политикой.
- **`read`/`write` — семантическое ПЕРЕСЕЧЕНИЕ областей путей** (§3.4). Вместо
  алгебры glob-масок (не замкнуты относительно пересечения) эффективная
  политика хранит слои: слой = OR-набор масок одной политики, между слоями —
  AND. Путь разрешён, если попадает во ВСЕ слои. Это точное пересечение
  без преобразования масок; пример из ТЗ (Global `**` ∩ Unit `src/**` ∩
  Project `src/backend/**` = `src/backend/**`) работает именно так.
- **Матчер**: нормализованные относительные пути, `/` как разделитель,
  `**` (включая переход через `/`), `*`, `?`, `[...]`. Регистр значим.
  `..`, абсолютные пути и пустые маски отвергаются на валидации.
- **`write` не подразумевает `read`** (это разные операции §3.2): путь,
  открытый только на запись, позволяет `write_file`, но не `read_file`.
  Практически политики почти всегда дают read шире write — вопрос открыт
  для экспериментов.
- **`PolicyVersion`** — стабильный отпечаток (sha256/12 hex) нормализованной
  эффективной политики; пишется в `RunInput`, в `run.started` и в аудит.

## 2. Наследование при делегировании (§6.2–6.3)

Сейчас дети получают конфиг через run-config, который ПЕРЕСЧИТЫВАЕТ политику
по org-позиции. Это может ослабить доступ, если политику изменили между
стартом родителя и ребёнка. В P0:

- `applyRunPolicy` морозит `Filesystem`+`PolicyVersion` в `RunInput`;
- `ResolveAgentRequest` несёт снимок родителя; `ResolveAgent` переопределяет
  им ребёнка (снимок побеждает свежий пересчёт);
- продолжение после turn-limit (`TurnLimitRestarts`) и team-слоты идут через
  тот же `resolve_agent` → тот же механизм.

Так «изменения политики не повышают полномочия уже запущенного процесса» —
всё дерево делегирования работает на снимке инициатора.

## 3. Влияние на существующие инсталляции

**Файлы.** Каноническое пространство не меняется (`/workspace` проекта),
поэтому накопленные файлы, uploads, артефакты и ссылки на них в чате
сохраняют смысл. Миграция файлов не нужна.

**Знания и опыт агентов.** Knowledge/hints ссылаются на пути и содержимое —
пути стабильны (§4.2), ничего не инвалидируется. Единственное изменение
поведения: если оператор задаст deny-область, а знания агента ведут в неё —
агент получит отказ на операцию (и это ожидаемая семантика, отказ должен
сопровождаться внятным сообщением и аудитом, чтобы не выглядеть как поломка).

**Политики.** Колонка `filesystem` добавляется аддитивно (JSONB, NULL).
`MergePolicies` для строк без правил не меняет результат. Существующие
инсталляции после апгрейда ведут себя одинаково до первого файлового правила.

**Бегущие workflow (Temporal).** `RunInput`/`ToolRequest` — JSON-пейлоады;
новые поля с `omitempty` реплеятся без ошибок, старые run-ы получают
`nil` = без ограничений. Совместимость в обе стороны сохраняется.

**Роль-ограничения (reviewer/qa/read-only).** Действующее поведение
(`requireWritableWorkspace`, `:ro` маунт) сохраняется как КОНСЕРВАТИВНОЕ
наложение: роль может только СУЗИТЬ (запретить запись), никогда — выдать.
ТЗ запрещает роль как основание выдачи полномочий — сужение этому не
противоречит и защищает старые инсталляции, где роль-ограничения
рассчитываются.

## 4. Риски и открытые вопросы (для экспериментов)

1. **Landlock на целевых платформах.** Sandbox — Linux-контейнеры; на macOS
   (Docker Desktop) и Windows/WSL2 ядро идёт виртуальной машиной Docker, и
   LSM Landlock может быть выключен в конфиге её ядра (проверить
   `grep landlock /proc/self/status` / лог `lsm=` внутри контейнера).
   ТЗ §5.3 требует либо безопасный отказ, либо явный альтернативный
   механизм — варианты: маленький setuid-less лаунчер с Landlock ABI ≥ 2
   внутри образа песочницы + честный fail-closed при недоступности
   (опциональный форс-флаг для лабораторных стендов), либо fallback на
   контрактные проверки поверх уже существующих маунтов (`:ro`, раздельные
   bind'ы) с громким предупреждением. Решение принимается по результатам
   прогона P1 на Linux, WSL2 и macOS.
2. **Производительность gateway.** Проверка пути на каждый read/write —
   дешёвая (glob-матчинг по спискам масок), но list/search-операции должны
   фильтровать, а не падать: каталог, где смешаны разрешённые и запрещённые
   файлы, должен отдавать разрешённые (решение в P1).
3. **Git-операции** (checkout/merge меняют дерево массово) — работают через
   `run_command`, т.е. через механизм P1; построчная проверка невозможна,
   только Landlock/маунты.
4. **Symlink-обходы** уже закрыты на уровне `resolveWorkspacePath` для
   встроенных инструментов; для shell остаётся Landlock (он не даёт
   «выйти» за права через symlink-цепочки).
5. **`write` без `read`** — см. §1; может упростить до «write включает read»,
   если практика покажет, что split только плодит отказы.

## 5. План этапов (соответствие ТЗ §10)

- **P0 (эта ветка):** модель правил + матчер + рестриктивное слияние,
  снимок политики в `RunInput`/`ToolRequest`, наследование при делегировании,
  `PolicyVersion` в журнале, тесты идентичности и совместимости.
- **P1:** enforcement — файловые инструменты ядра (gateway + аудит отказов),
  Landlock-исследование и лаунчер в песочнице, паритет read_file ↔ shell.
- **P2:** workspace_claims в `PlanTask`, детекция пересечений, git worktree,
  интеграция с проверками и журналированием.
- **P3:** не-Git изоляция, UI правил и эффективных полномочий, диагностика
  конфликтов.
