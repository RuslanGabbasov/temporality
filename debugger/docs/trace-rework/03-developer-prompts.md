## T1 (developer): рефакторинг загрузки вкладки «Запуски», анти-N+1, K-2/K-3

**Цель:** устранить жадную загрузку вкладки «Запуски» debugger по NFR-1…NFR-8 и дефекты K-2/K-3.
**Контекст (проверено Лидом):** `src/AgentRuns.tsx` (~1460 строк): список ранов строится 4 сканами журнала по 500 событий (`:519–526`), на каждую строку списка — `fetch /v1/agent/runs/{id}` (N+1, `:549–551`); при выборе рана — события всех детей `Promise.all(childIDs.map(runEvents))` (`:606–622`); ошибки части запросов глушатся `.catch(() => ({events: []}))` (`:523–526`, K-3); polling выбранного рана каждые 10 с (`:655`) — сохранить; догон курсоров `runEvents` (`:604`) — сохранить. Сервер: `cmd/agent-kernel/main.go` (Go), batch-эндпоинта списка ранов нет — добавить (курсорная пагинация, страница 50–100, статус/terminal-событие в строке).
**Объём:** 1) серверный `GET .../runs` (batch, курсор, статус в строке) для строк списка; 2) открытие вкладки ≤3 сетевых запросов (убрать 4 скана и N+1); 3) выбор рана — 1 запрос страницы таймлайна (50–100 событий, курсор, догрузка по скроллу/курсору), result/costs/trajectory — лениво (открытие вкладки/раскрытие); 4) NFR-3: события детей не грузить целиком — мета-строка делегирования + ленивая догрузка; 5) NFR-4: AbortController на все запросы, кэш/дедупликация по `run_id`; 6) NFR-5: виртуализация таймлайна (окно 50–100 строк, ≤2000 DOM-узлов), тяжёлые тексты лениво; 7) NFR-6: polling/SSE только выбранного рана, интервал ≥5 с, `document.hidden` → пауза (включить в polling, если отсутствует); 8) K-3: `.catch(() => ...)` → признак `partial: true` в состоянии + индикатор «статусы недоступны» в UI + логирование причины; 9) NFR-8: новые строки через i18n ru+en.
**Готовность (DoD):** бюджеты запросов закреплены perf-guard тестами (открытие ≤3, выбор =1); новые unit-тесты (загрузка/батч/курсор/partial); все существующие тесты зелёные; `npm run build` без новых замечаний; поведение polling и семантика событий не изменены; отчёт по форме (а–г).
**Формат отчёта:** `debugger/docs/trace-rework/reports/t1-report.md`.

**Контекст:** источник истины — `src/eventCatalog.ts` (15 групп, ~120 типов); типы вне каталога: псевдо-инструменты (`run_command`, `skill_*`, `mcp__*`, `browser`, `send_file`…), streaming-типы `model.text_delta`/`model.reasoning` (НЕ строки таймлайна — питают live-строку вызова модели, `AgentRuns.tsx:1223`); `explainKernelError` (`eventSummary.ts:27–35`) — для причин ошибок; K-1: `AgentRuns.tsx:1021` `json(operation?.arguments ?? details)` — сырой JSON в UI → human-форма в слой 2, сырой JSON только в слое 3; нелокализованный `by ${approver}` (`eventSummary.ts:409`) — устранить.
**Объём:** 1) декларативная таблица (код + данные), покрытие 100% типов каталога + псевдо-инструменты + streaming-типы; generic-шаблон для незнакомых типов (семантика, не сырой JSON); 2) слой 1 — строка: иконка/цвет по смысловой категории, заголовок ≤120 символов, ключевой факт, длительность, статус; название типа события не показывать (кроме слоя 3); 3) слой 2 — инлайн-раскрытие «что произошло и что делать»: аргументы human-формой, результат, причина ошибки, ссылки (дочерний ран / знание / `artifact://` для артефактов / `console://` для вывода), прогресс/вывод для долгих операций; 4) слой 3 — «Сырое событие (JSON)», свёрнуто, в конце детализации, доступно всем пользователям трассы; 5) сводки по группам из `01-spec-validated.md` §3B (runs: `run.note_dropped` — CTA «повторить»; model: `attempt/nudged` жёлтым; tools: файловые — диф-превью, `tool.failed/blocked` — причина + CTA; delegation/plans — дерево лениво, транзиции плана свёрнуты, комментарий ревьюера при `rejected` видим; approvals/human — 1 строка на пару запрос/решение, карточка-CTA; knowledge/hints — агрегаты «3 подсказки, 2 использованы»; artifacts — имя/версия/ссылка; secrets — только имя/статус/причина, `secret.value_set` → «значение задано» без payload; mcp/triggers/intake — конвейер одной строкой; skill/agent.definition/agent.evaluation — «Эволюция агента», гейт-блокировки красным; saga — свёрнуто; ops-шум — свёрнут/фильтруем); 6) K-1: human-форма аргументов в слое 2; 7) кнопка «Детализация» удалена (раскрытие кликом по строке/клавиатурой); 8) инвариант `secret.*` — значения не отображаются ни на одном слое (автотест redaction); 9) i18n всех новых строк ru+en (включая замену `by ${approver}`).

## T3 (developer): стрим вывода `run_command`, URI `console://<operation_id>`

**Цель:** live-стрим stdout/stderr команды в слое 2 + буфер хвоста; адресация `console://<operation_id>`.
**Контекст (проверено Лидом):** сервер сейчас буферизует вывод до завершения команды: `kernel/sandbox/docker.go:340–357` (`result.Output` собирается после `cmd.Run()`) — live-стрим требует серверной поддержки; прецедент live-потока — ephemeral token stream (`cmd/agent-kernel/main.go:3224`); `journalStream.ts` — SSE-паттерн клиента; решение заказчика: без персистентности вывода (live + буфер хвоста), redaction/allowlist на вывод НЕ требуется (секреты вне песочниц), инвариант `secret.*` остаётся.
**Объём:** 1) сервер: in-memory кольцевой буфер на `operation_id` (лимит 256 КБ / 2000 строк, отброс старых с маркером), эндпоинт тейла (SSE либо опрос — требование допускает «SSE/интервал»): возвращает хвост/диапазон + live-фреймы пока команда работает; без записи на диск; стоп по завершении операции (к `tool.completed/failed`); 2) клиент: лениво — подписка только при раскрытии события выбранного рана; live-тейл с отменой через `AbortController`; пауза при `document.hidden`; авто-перемотка к хвосту с ручной паузой; первые 64–256 КБ, «Показать полностью» — дозапрос диапазона; вкладки/префикс stdout и stderr; подсветка ошибок; кнопка «копировать»; маркер усечения буфера; 3) URI-контракт: ссылка `console://<operation_id>` в детализации; в UI нет `artifact://`-ссылок на консольный вывод; 4) ограничение (без хранения вывода): серверный поиск по выводу невозможен — явная пометка в UI (подсказка у поиска) и в отчёте; 5) i18n новых строк ru+en.
**Готовность (DoD):** unit-тесты стриминга (буфер хвоста/усечение, диапазонный дозапрос, `console://`-адресация, отмена/стоп по `tool.completed`); поведение без персистентности (после завершения — хвост из буфера); регрессия тестов зелёная; `npm run build` без новых замечаний; отчёт по форме (а–г). Если серверную часть завершить не удаётся — клиентский контракт полный, в отчёте статус «сделано, но не проверено» с точным описанием разрыва.
**Формат отчёта:** `debugger/docs/trace-rework/reports/t3-report.md`.

**Готовность (DoD):** тесты фильтров/поиска/URL-состояния; новые unit-тесты (поиск по буферу вывода); регрессия зелёная; `npm run build` без новых замечаний; отчёт по форме (а–г) — сводный по T1–T4.
